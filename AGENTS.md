> Guidance for AI coding agents working in this repository.

## Project status

Событийная петля с актором диалога (процессная модель + LLM-роутер), персистом в SQLite и фоновыми задачами-процессами работает. Реализовано:

- монорепо из двух проектов: библиотека `core/` (`octoforge-core`) и web-приложение `web/` (`octoforge-web`) — у каждого свой `pyproject.toml`, зависимости и тесты;
- петля как поток событий: `AgentLoop.stream(history, control, context) -> AsyncIterator[LoopEvent]` — токены, вызовы скилов, финал, отмена; eager-исполнение тулов по готовности аргументов (события `ToolCallStarted`/`Ready`/`Broken` в стриме, конкурентный запуск, история строго в порядке вызовов, fallback на старт после `StreamFinished`) и idle-watchdog стрима (`stream_idle_timeout`, конфиг `OF_LLM_STREAM_IDLE_TIMEOUT_SECONDS`); см. `docs/streaming.md`;
- управление прогоном: `LoopControl` (инъекции сообщений + отмена с сохранением частичного ответа);
- процессная модель диалога (этап E): актор `ConversationRunner` владеет нарративом (user-сообщения + финалы процессов + system-уведомления; только он персистится) и процессами (fg/bg, в памяти); broadcast — события форграунда + маркеры `ProcessSuspended`/`ProcessResumed`/`ProcessCompleted`; `ConversationManager` — runners по `(user_id, channel)` (get-or-create), конструктор через `RunnerConfig` (промпты — через порт `PromptProvider`);
- промпты ядра за портом `PromptProvider` (`agent/prompts.py`; дефолт — `StaticPromptProvider` поверх вшитых констант, роутерный промпт вынесен из `LLMRouter` в провайдер); web-слой добавляет `FilePromptProvider` (`OF_SYSTEM_PROMPT_SOURCE`/`OF_ROUTER_PROMPT_SOURCE`, формат `file:/path`, перечитывание на каждый get, fallback на вшитый дефолт);
- LLM-роутер (`agent/router.py`): порт `MessageRouter` (пакет `RouteOp`: INJECT/START_NEW/CANCEL/PROMOTE), `LLMRouter` — one-shot `complete()` с tool `route(ops)`, таймаут (`OF_ROUTER_TIMEOUT_SECONDS`), валидация ops, фолбэк (при активном форграунде — INJECT, не START_NEW); детерминированный guardrail: пакет с INJECT теряет все START_NEW (инъекция не уводит вопрос в фон); guardrail лимита процессов (`OF_MAX_PROCESSES`) в акторе;
- персист: SQLAlchemy async + SQLite, пакет `db/` (Base + `UTCDateTime`, ORM-модели dialogs/messages/tasks, фабрики engine/session, репозитории); схема — Alembic (`bootstrap_schema`: upgrade до head при старте с явным commit'ом транзакции миграций, pre-Alembic БД штампуется на baseline и догоняется — ALTER-миграции добавляют колонки условно; `create_all` — fallback и тесты); `seq` сообщений присваивается атомарно подзапросом в INSERT;
- фоновые задачи = фоновые процессы актора (этап E): `TaskKind.RUN`, `TaskStatus` (+CANCELLED), порт `TaskStore` (+cancel/is_cancelled/count_active; `next_pending` и глобальный `TaskRunner` удалены); спавн — порт `TaskSpawner` (`tasks/spawner.py`), bound-реализация в акторе; скилы `task_spawn`/`task_list`, уведомление о завершении с отметкой `result_delivered` (репорт-прогон или инъекция; репорт-прогон завершает ветку user-nudge'ом — на system-хвост часть моделей отвечает пустотой); системный промпт процессов дополняется текущей датой UTC (`_with_current_date`);
- скилы: `Skill`/`SkillSpec`/`SkillContext(user_id, channel, dialog_id, task_spawner?)`/`SkillRegistry`, типы `BASIC|DYNAMIC`; базовые `http_request`, `task_spawn`, `task_list`, `instructions_search`, `instruction_save`, `external_call`, `data_put`, `data_query`, `data_forget`, `memory_store`, `memory_search`, `memory_delete`, `cron_create`, `cron_list`, `cron_delete`, `cron_pause`, `cron_resume`, `web_search` (через порт `SearchProvider` из модуля `search/`; дефолт — `SerperSearchProvider` для serper.dev, при `OF_SERPER_TOKEN`);
- LLM-клиент: `complete()` + `stream()` (SSE, tools/tool_calls); порт `EmbeddingClient` с двумя бэкендами — локальный sentence-transformers `llm/local_embeddings.py` (как в b2e: bi-encoder, L2-нормализация, вычисление в `asyncio.to_thread`) и OpenAI-совместимый `llm/embeddings.py` (POST /embeddings); выбор — `OF_EMBEDDING_BACKEND` (конфиг `EmbeddingConfig` рядом с `LLMConfig`); порт `RerankerClient` + cross-encoder `llm/reranker.py` (MPS при наличии);
- инструкции (этап B): обособленный пакет `instructions/` (граница `api.py` — Protocol `InstructionService`: `search`/`save`/`get_by_name`; порт хранилища `InstructionStore` + runtime-checkable capability `InstructionVectorSearch` для поиска на стороне БД; локальная реализация — `SqlAlchemyInstructionStore` (таблица `instructions`), cosine-ранжирование + буст точного title + опциональный cross-encoder реранк шортлиста (`rerank_candidates`), сидирование); исполнение внешних вызовов — вне модуля: `net/` (`ExternalCallExecutor` поверх tool-записей, `SsrfGuard`, whitelist-авторизация из composition root);
- датасеты (этап C): обособленный пакет `datasets/` (граница `api.py` — Protocol `DatasetService`; порт хранилища `DatasetStore` + capability `DatasetVectorSearch`; локальная реализация — `SqlAlchemyDatasetStore` (таблицы `datasets`/`dataset_records`), валидация записей по JSON-схеме, cosine-поиск по дескрипторам с бустом точного имени, owner-изоляция на уровне SQL); скилы `data_put` (create-if-absent)/`data_query`/`data_forget`; дескрипторы участвуют в `instructions_search`; см. `docs/data-store.md`;
- память (этап D): обособленный пакет `memory/` (граница `api.py` — Protocol `MemoryStore`, DTO `Memory`, `MemoryScope(USER|GLOBAL)`; таблица `memories`, `user_id` NULL = глобальный скоуп, upsert по (owner, key) в самом сторе — unique-констрейнт NULL не ловит; LIKE-поиск «свои + глобальные», без эмбеддингов); скилы `memory_store`/`memory_search`/`memory_delete`; автоинъекция в контекст — следующая итерация; см. `docs/dialogs.md`;
- web: dialog API (`POST /api/dialog/messages`, `POST /api/dialog/cancel`, `GET /api/dialog/events` SSE) с заголовком `X-User-Id` (доверенная строка, без аутентификации), чат-UI со стримом, маркерами процессов и кнопкой «Стоп»; канал `"web"` объявлен в composition root;
- крон-задачи (этап F + итерация надёжности): обособленный пакет `cron/` (граница `api.py` — порты `CronStore`/`CronWaker`/`Scheduler`, DTO `CronJob` (+`one_shot`/`last_status`/`last_error`/`retry_count`), `compute_next_fire`/`count_missed` на croniter+zoneinfo; таблица `cron_jobs`; `CronScheduler` — реализация порта `Scheduler`: asyncio-цикл с CAS-арендой по lease TTL, coalesce пропущенных, разбросом и лимитом догонялки; `list_due`/`claim`/`complete_fire` + математика расписаний — публичный контракт для альтернативных движков); выстрел — `ConversationManager.wake` → фоновый процесс с `cron_job_id` в `Task.input` (переполнение лимита → системная заметка); исход процесса возвращается в стор: актор репортит через порт `TaskOutcomeListener` → `CronOutcomeReporter` (`cron/reporter.py`) → `record_fire_result` (ретрай с backoff'ом при фейле — `OF_CRON_RETRY_LIMIT`/`OF_CRON_RETRY_BACKOFF_SECONDS`, удаление one-shot после первого DONE, сброс серии); `cron_create` дедупит идентичные задачи и принимает `one_shot`; HTTP API `/api/cron` (query-параметры, скоуп по `X-User-Id`) — для внешних клиентов; агент управляет задачами нативными скилами `cron_create`/`cron_list`/`cron_delete`/`cron_pause`/`cron_resume` над `CronStore` (работают и в standalone без HTTP; HTTP-сид-тулы крона удаляются миграцией `migrate_cron_tools_to_native` при старте, порт `InstructionService` += `delete`); см. `docs/cron.md`.
- telegram-адаптер (этап G): вторая поверхность — пакет `web/src/octoforge_web/telegram/` (Bot API на чистом httpx, без aiogram: порт `TelegramClient` + `TelegramBotClient`; long-poll `TelegramPoller` с offset в памяти, backlog-drain и backoff); канал `"telegram"`, `user_id = "tg:<telegram user id>"`, только личные чаты; `TelegramBridge` рендерит события runner'а в черновое сообщение с throttle-правками (`OF_TELEGRAM_EDIT_THROTTLE_SECONDS`), статус-строками скилов и чанкером 4096; markdown ответов конвертируется в Telegram-HTML (`markdown.py`: `markdown_to_telegram_html` + `split_html_safe` — срез без разрыва тегов), отправка с `parse_mode="HTML"`, на «can't parse entities» — фолбэк в plain text; команды `/start`/`/cancel`; мосты прогреваются из БД при старте (`list_user_ids_by_channel`), чтобы крон-выстрелы доставлялись; выключен без `OF_TELEGRAM_BOT_TOKEN`; standalone-режим `python -m octoforge_web.telegram` — только бот и крон-планировщик на общем composition root'е (`runtime()` в `main.py`), HTTP API и порт не поднимаются; см. `docs/design.md`.
- компакция контекста диалога (дизайн — `docs/context.md`): обособленный пакет `context/` (граница `api.py` — порты `ContextCompactor`/`SummaryStore`/`MessageArchive`, DTO `DialogueSummary`/`ArchivedMessage`/`ArchiveFilter`; `SqlAlchemySummaryStore` реализует оба стора — таблица `dialog_summaries` + read-only чтение архива `messages`); ветка процесса собирается компактором из `RunnerConfig.compactor` (обязательный; `NoopContextCompactor` — дефолт в тестах): блок тем (все саммари диалога одним system-сообщением) + горячий хвост (`seq > max(seq_to)`, дословно, из нарратива актора); переполнение хвоста (`OF_CONTEXT_HOT_MAX_CHARS`, символы) триггерит фоновую asyncio-компакцию `LlmContextCompactor` — старейшие сообщения хвоста (до `OF_CONTEXT_COMPACT_TARGET_CHARS`) одним one-shot `complete()` в запись `dialog_summaries` с тегами тем; guard «одна компакция на диалог», фейл = warning-лог (диалог не страдает), отмена при `stop()` runner'а; срез сегмента — только между сообщениями и никогда внутри salvaged-пары (`INTERRUPTED_NOTE`); скил `history_search` (LIKE-подстрока по архиву текущего диалога, фильтры темы/дат, лимиты `OF_HISTORY_SEARCH_DEFAULT_LIMIT`/`OF_HISTORY_SEARCH_MAX_LIMIT`); системный промпт — правило 14 про поиск по истории;
- переиспользуемый composition root (этап P5, `docs/modularity.md` — все этапы P1–P6 закрыты): `core/composition.py` — builder-функции сборки (`build_llm_client`, `build_instruction_service`, `build_dataset_service`, `build_external_executor`, `build_skill_registry`, `build_agent_loop`, `build_compactor`, `build_router`, `build_cron_outcome_reporter`, `build_runner_config`, `build_conversation_manager`, `build_cron_scheduler`) + бандлы `SkillLimits`/`SkillStores`/`SkillServices`/`RunnerOptions`; только порты и конфиги, без fastapi/web-Settings/Telegram; `runtime()` в web — дефолтная сборка поверх builder'ов, сторонний корень собирается из них же без копирования; `octoforge_core/__init__.py` экспортирует builder'ы и порты модульности;

Не реализовано: пользователи/аутентификация (user_id — доверенная строка от клиента), редоставка недоставленных результатов задач при старте и реанимация/фейл задач, осиротевших при рестарте (процессы — в памяти, PENDING/RUNNING теряют исполнителя), влияние usage/success-статистики на ранг поиска инструкций и http-реализация фасадов `InstructionService`/`DatasetService`/`MemoryStore` (выделенный сервис), автоинъекция памяти в контекст, HTTP wake endpoint и служебные токены для крона (в standalone — in-process wake). План — `docs/design.md`.

## Project overview

OctoForge — мультипользовательский LLM-агент: Python, FastAPI, SQLAlchemy (async, SQLite), скилы на исполняемых Jinja-шаблонах, знания в БД, фоновые задачи с уведомлениями. Детали — `docs/design.md`.

## Repository layout

- `core/` — библиотека `octoforge-core` (src-layout): домен, порты, `composition.py` (переиспользуемые builder'ы сборки — `build_skill_registry`, `build_conversation_manager` и др.; только порты/конфиги, без fastapi и web-Settings), `agent/` (events/control/loop/router/prompts/runner), `skills/` (base/registry/basic), `tasks/` (models/store/spawner/errors), `llm/` (events/openai/embeddings/local_embeddings/reranker — порты `EmbeddingClient` и `RerankerClient`, локальный бэкенд на sentence-transformers), `db/` (base/models/engine/repositories), `instructions/` (модуль инструкций: api/models/store/ranking/local/seed), `datasets/` (модуль датасетов: api/models/validation/store/ranking/service), `memory/` (модуль памяти: api/models/store), `context/` (модуль контекста: api/models/store/compactor/prompts — компакция нарратива и чтение архива), `cron/` (модуль крон-задач: api/models/store/scheduler/waker), `search/` (порт `SearchProvider` + SerperSearchProvider), `net/` (SSRF-гвард, исполнитель внешних вызовов). Не импортирует fastapi; sqlalchemy — только в `db/` и SQL-сторах (`db/repositories.py`, `instructions/store.py`, `datasets/store.py`, `memory/store.py`, `context/store.py`, `cron/store.py`).
- `web/` — приложение `octoforge-web` (src-layout): FastAPI-обёртка, `api/` (dialog/cron/sse/schemas), `prompts.py` (`FilePromptProvider`), `telegram/` (адаптер поверхности Telegram: models/client/bridge/poller, `__main__` — standalone-запуск без HTTP API), статика, composition root в `main.py` (общий `runtime()` для web и standalone). Зависит от `octoforge-core`.
- Корень: `Makefile`, `README.md`, `.env.example`, `docs/`.

## Build and test commands

- `make install` — создать `.venv` и поставить оба проекта editable с dev-зависимостями
- `make check` — ruff (lint + format check) → mypy strict → pytest для обоих проектов
- `make lint` / `make typecheck` / `make test` / `make format` — шаги по отдельности
- `make run` — uvicorn с автоперезагрузкой (нужен `.env` с `OF_LLM_API_KEY`)
- `make run-telegram` — только Telegram-бот, без HTTP API (long polling, порт не открывается; нужен `OF_TELEGRAM_BOT_TOKEN`)

Конфиги ruff/mypy/pytest — в `core/pyproject.toml` и `web/pyproject.toml` соответственно.

## Code conventions

Обязательны во всём коде проекта:

1. **UTC everywhere** — все даты timezone-aware UTC. Время получаем только через хелпер `utc_now()` (`octoforge_core/time.py`); naive datetime запрещены. На SQLite — TypeDecorator, принудительно выставляющий UTC при чтении/записи.
2. **Полная типизация** — аннотации на всех функциях (аргументы и возвращаемое значение) и атрибутах классов. Контроль: ruff ruleset `ANN` + mypy strict. `Any` только внутри контейнеров (`dict[str, Any]` на JSON-границе), голый `Any` в аннотациях запрещён (ANN401).
3. **Объекты, не словари** — данные носим в доменных объектах (dataclass/pydantic) и ORM-моделях. `dict` допустим только на самой границе (JSON in/out) и сразу валидируется в объект.
4. **Перечисления — Enum** — статусы, виды, роли и т.п. объявляем через `StrEnum`; в БД хранится значение enum'а.
5. **Никакой магии** — строковые и числовые литералы со смыслом — именованные константы или конфиг; лимиты — в конфиге. В тестах HTTP-коды — через `HTTPStatus`.
6. **Тесты в том же изменении** — фича или фикс без тестов не считается сделанным. pytest + pytest-asyncio; внешние системы (LLM, HTTP) мокаем.
7. **Чистая архитектура** — слои: библиотека `core/` (домен, сервисы, порты-Protocol + адаптеры) → приложение `web/` (FastAPI-адаптеры). Зависимости только внутрь: библиотека не импортирует fastapi; внешние клиенты попадают в сервисы через Protocol-порты.
8. **Линтер перед тестами** — порядок проверки: `ruff check` → `ruff format --check` → `mypy` → `pytest`. Одна команда: `make check`.
9. **Контроль сложности** — ruff: `C901` (цикломатическая сложность ≤ 10), `PLR0915` (≤ 50 statements), `PLR0911` (≤ 6 return'ов). Превышение = дробим функцию по ответственности, а не отключаем правило.
10. **Ядро отдельно, web отдельно** — физически разные проекты: `core/` и `web/`. Web — тонкий адаптер, вся логика в библиотеке.
11. **DI (Dependency Injection)** — зависимости приходят снаружи: через конструктор, параметры или `Depends` на web-слое. Создавать зависимости внутри методов запрещено; сборка графа объектов — в одном месте (composition root: `web/src/octoforge_web/main.py` и фабрики).
12. **Языки** — общение с пользователем и вся документация (`docs/`, `README.md`, этот файл) — на русском. Коммиты, docstrings и комментарии в коде — на английском.

## Workflow rules

- **Git-коммиты — только с явного разрешения пользователя.** Спрашивать разрешение каждый раз перед `git commit` и любой другой git-мутацией (push, reset, rebase и т.д.).
- **Документация обновляется вместе с кодом.** Каждое изменение, меняющее логику, и каждая новая идея дописываются в `docs/design.md` (а при смене конвенций, структуры или команд — и в этот файл) в том же изменении.
