## Project status

An event loop with a dialog actor (exchange model + LLM router), SQLite persistence, and background task-processes all work. Implemented:

- a monorepo of two projects: the `core/` library (`octoforge-core`) and the `web/` application (`octoforge-web`) — each with its own `pyproject.toml`, dependencies, and tests;
- the loop as an event stream: `AgentLoop.stream(history, control, context) -> AsyncIterator[LoopEvent]` — tokens, tool calls, final, cancellation; eager tool execution as soon as arguments are ready (`ToolCallStarted`/`Ready`/`Broken` events in the stream, concurrent execution, history strictly in call order, fallback to start-after-`StreamFinished`) and a stream idle watchdog (`stream_idle_timeout`, config `OF_LLM_STREAM_IDLE_TIMEOUT_SECONDS`); see `docs/reference/agent-loop.md`;
- run control: `LoopControl` — cancellation only, preserving the partial answer (the injection channel was retired by the pull model: a process branch re-reads the narrative on every iteration);
- the dialog exchange model (rewritten 2026-07-28; the authoritative doc is `docs/reference/exchanges.md`): an **exchange** is a durable obligation to the user — their question, its clarifications and the final answer — a row in the `exchanges` table plus `messages.exchange_id`, statuses OPEN → IN_PROGRESS → ANSWERED / AWAITING_USER / CANCELLED / FAILED; exchange ≠ task: a run can finish DONE while its exchange stays open (it asked the user something). The actor-broker `ConversationRunner` owns the narrative (user messages + run finals + broker notes; only this is persisted) and the processes (in memory; every process is backed by a task, `process.id == task.id`: ANSWER — owes an exchange an answer, carrying `exchange_id` in `task.input`, RUN — task_create/cron); a branch = `[system] + a compactor snapshot of the narrative + a private working suffix` and re-reads the narrative on every `IterationStarted` (pull model; no change — byte-identical); branch roles derive from durable exchange state (`agent/branch.py:render_branch`): the run's own question is marked as its task, later messages of the same exchange as clarifications, and questions of OTHER live exchanges are DROPPED from the branch entirely (a "someone else is on this" mark still pulled the model into answering — measured live); there is NO foreground: every answer run streams concurrently, each event enveloped as `ConversationEvent(dialog_id, seq, payload, exchange_id)` so transports keep one draft/bubble per exchange (Telegram threads each answer as a reply to its question and resolves a user's reply back to its exchange deterministically via `reply_to_exchange_id`); the `ask_user` tool parks the exchange AWAITING_USER (the question delivers immediately, jumping the outbox queue; the run's final does not close the exchange) and the user's reply resumes it with a fresh run; an event-driven nudge quotes the pending question when a new message arrives while another exchange has been AWAITING_USER for over 5 minutes; a message that arrived after a run's last narrative sync reopens the exchange to OPEN and gives it a fresh run (this replaced the watermark-requeue heuristic); `cancel()` bypasses the inbox (a routing LLM call would head-of-line block it) and stops ALL answer runs — RUN tasks keep going; `ConversationManager` — runners keyed by `(user_id, channel)` (get-or-create, memoized per-key builds instead of one global lock across DB work), built via `RunnerConfig` (prompts through the `PromptProvider` port); graceful shutdown — `ConversationManager.stop_all()` from `runtime()` (web); startup recovery reopens stranded IN_PROGRESS exchanges to OPEN (AWAITING_USER keeps waiting for the human), restarts orphaned tasks and redelivers undelivered results; 2026-07-26 audit fixes still hold: the loop races the cancel flag against both the stream wait and the tool wait; _broadcast never drops critical events (terminals/process markers evict the oldest queued event on a full subscriber queue) and _flush_deliveries stamps delivered_at only when the terminal reached ≥1 queue; the in-memory narrative holds only the hot tail (initial load via compactor.compacted_boundary + list_after, `AssembledContext.tail_count` → `_trim_narrative` on every re-assemble; message-to-exchange ownership lives in the DB, not in-memory id sets); instruction ranking is numpy-vectorized and runs in a worker thread with GIL-friendly chunked conversion (was an 850 ms event-loop freeze at 10k records); reply threading rides `source_client_message_id`;
- per-user secrets (`secrets/` module, 2026-07-26): Fernet-encrypted at rest (`OF_SECRETS_KEY`), value leaves the store only via `resolve(user, code, host)` with a hard host binding; endpoint records declare `auth: {secret, header, format}` and the executor injects exactly one header at request time — substitution exists ONLY in the admin-authored record template, never in agent-supplied values (exfiltration channel otherwise); response bodies are scrubbed of value echoes; ingestion is the /secrets Telegram command intercepted before the dialog pipeline, replying with a one-time link (`SecretLinkService`, 10-min TTL) to the token-authenticated /secrets.html form outside the operator Basic gate;
- the system-skill registry is the code default; an installation tunes it with a **file overlay** (`OF_SYSTEM_SKILLS_SOURCE=file:...`, `web/skill_overlay.py`): JSON entries that `append` to, replace, or add registry records before the startup sync — localized trigger phrases and house rules land without a rebuild and without touching core (measured need: English core scenarios ranked 9-15 for Russian phrasings of the same intent, 3-4 after the overlay);
- core prompts behind the `PromptProvider` port (`agent/prompts.py`; default is `StaticPromptProvider` over hardcoded constants, the router prompt was moved out of `LLMRouter` into the provider); the web layer adds `FilePromptProvider` (`OF_SYSTEM_PROMPT_SOURCE`/`OF_ROUTER_PROMPT_SOURCE`, `file:/path` format, re-read on every `get`, falls back to the built-in default); the system prompt's first three rules make **retrieval precede action** (`recall` first — one search covering skills, knowledge, dataset descriptors and the user's memories (endpoints only with an explicit type=endpoint — late binding via endpoint_get); a found record is binding; no trial-and-error) — a measured fix for the model answering from its own head, and the same policy is repeated in the tool descriptions of `recall`/`http_request`/`web_search`, which are always in context while scenarios are not; keep both in sync when either changes;
- LLM router (`agent/router.py`): routing answers one question — *whose is this message?* The `MessageRouter` port `route(exchanges, message, max_exchanges) -> RouteDecision` with `RouteAction` NEW (the message opens its own exchange; the default) / CONTINUE (it belongs to an existing exchange — the old INJECT and "answer to a clarifying question" collapsed into one; `exchange_id` required) / COMMAND (pure control, nothing to answer), plus `cancel_ids` — exchanges the user explicitly asked to stop; the input is `ExchangeInfo` snapshots (id, title, status, pending_question, age_seconds): the router reasons over exchanges, human-text entities, not process ids; one message belongs to exactly one exchange, so op batches and the INJECT-kills-START_NEW guardrail are gone; deterministic layers live in the actor and skip the LLM entirely — an explicit transport reply (`reply_to_exchange_id`) names its live exchange outright, and with no live exchange the answer is NEW; `LLMRouter` — a one-shot `complete()` with the `route` tool under a timeout (`OF_ROUTER_TIMEOUT_SECONDS`); the safe default is NEW: every failure (LLM error, timeout, no tool call, unknown action, CONTINUE into an unknown exchange) degrades to a new exchange with a WARNING log while keeping valid cancel_ids — a redundant NEW is a visible, correctable extra answer, a wrong CONTINUE feeds the question into someone else's run (silence); decisions are logged together with their candidates; the exchange-count guardrail (`OF_MAX_PROCESSES`) lives in the actor; router-side skill presearch (searches + `PresearchPort`) was removed on 2026-07-21 — scenarios only reach the context through `recall` during a run (see `docs/reference/instructions.md`);
- persistence: async SQLAlchemy + SQLite, the `db/` package (Base + `UTCDateTime`, ORM models for dialogs/messages/tasks, engine/session factories, repositories); schema via Alembic (`bootstrap_schema`: upgrades to head at startup inside an explicit migration-transaction commit; pre-Alembic databases are stamped at the baseline and caught up — ALTER migrations add columns conditionally; `create_all` is the fallback used by tests); message `seq` is assigned atomically by a subquery inside the INSERT;
- background tasks are background actor processes (stage E): `TaskKind` (RUN — task_create/cron; ANSWER — the internal mechanics of replying to a user message, invisible to tools), `TaskStatus` (+CANCELLED — a terminal state for both processes and `cron_jobs.last_status`), the `TaskStore` port (`tasks/store.py`: add/get/list/mark_done/mark_failed/mark_cancelled/delete/list_orphaned/list_undelivered/mark_delivered — task rows are kept forever; `delivered_at` records delivery of the result to the transport, `list_undelivered` = DONE/FAILED with `delivered_at IS NULL`; a final is linked to its task via `messages.task_id`, migration `d1e5f9a3b247`; a task's parent link lives in `input`: `{cron_job_id, fired_at}` for cron fires, `{source_message_id, exchange_id}` for answer tasks (the id of the user's question message and the obligation the run owes; `ChatMessage.id` — the DB row id, pure DB metadata, excluded from equality)); spawning goes through the `TaskSpawner` port, stopping through the `TaskDeleter` port (both in `tools/base.py`, bound implementations live on the actor; a tool cannot delete its own owning task — rejected via `ToolContext.owner_task_id`); tools `task_create`/`task_list`/`task_delete` (`task_list` shows RUN tasks that are in flight or awaiting delivery — delivered and answer tasks are hidden; `task_delete` only stops a task — the row stays CANCELLED); result delivery with no LLM involved and no foreground gate: a RUN task's final or a broker notice is placed in the outbox (`_pending_deliveries`) and goes out whole immediately (DONE → TextDelta + Finished, FAILED → Failed) as long as **at least one subscriber is attached** (a broadcast into zero queues reaches nobody, so stamping it delivered would lose the result for good — the outbox is purely the no-subscriber retention guarantee and drains on the next `subscribe()`, which enqueues a `_Flush` command; an `ask_user` question jumps the queue; live stream events are never replayed, only the outbox is); an answer run's final has already been streamed live into its per-exchange message — only `delivered_at` gets set; a limit-exceeded rejection is a templated broker notice delivered the same outbox way; startup recovery — `ConversationManager.recover_interrupted()`, called from `runtime()` before the scheduler starts: PENDING/RUNNING → restarted as a background process (`restart_task`, queue mode; exceeding the limit → mark_failed plus a delivered Failed); a cron-tagged outcome goes through `TaskOutcomeListener` once the restarted process finalizes; undelivered results are re-delivered through the normal `_ProcessTerminated` path (`request_result_delivery`, idempotent on `delivered_at`); the current date/time is an envelope on the branch's last message (`_with_date_envelope`: the system prompt stays byte-stable for prefix caching, the narrative/persisted copy is untouched; see `docs/guides/performance.md`);
- tools: `Tool`/`ToolSpec`/`ToolContext(user_id, channel, dialog_id, task_spawner?, task_deleter?, owner_task_id?)`/`ToolRegistry` (no `SkillOrigin` — removed; `specs(context?)` is a shared duck-typed visibility hook: a tool with an optional `visible_to(context) -> bool` attribute only appears in the tool list when it returns True; - LLM client: `complete()` + `stream()` (SSE, tools/tool_calls); a typed error taxonomy in `llm/errors.py` (rate_limit/auth/quota/context_overflow/provider_internal/transport; body markers are checked before the HTTP status — a 429 with `insufficient_quota` is a fatal QuotaError; - forwarded messages are **material**, not questions (`MessageKind.MATERIAL`, column `messages.kind`, NULL = the user's own words): the Telegram poller reads `forward_origin`, bakes attribution into the text and hands it over as material; the actor never opens an obligation or starts a run for it. Material joins the dialog's single `COLLECTING` exchange (durable — no in-memory buffer or timer holds correctness), each arrival touching its `updated_at`, which is the quiet clock. `CollectingSweeper` (`agent/collecting.py`, `OF_MATERIAL_QUIET_SECONDS` / `OF_MATERIAL_SWEEP_INTERVAL_SECONDS`) nominates collections quiet for the window and the actor promotes them (re-checking status and quietness — the sweep never writes, or it would race a run start). At promotion one router call may re-parent the whole batch into another live exchange; that decision's `cancel_ids` are ignored and `COMMAND` means "no target" — forwarded text is untrusted input. A question routed CONTINUE into the collection adopts it and answers immediately; `/cancel` drops it. `_Unseen` (NONE/MATERIAL_ONLY/SPOKEN) keeps a forward burst into a live exchange from reopening it once per message;

the history-search method is documented as the `history_lookup` system skill;
- a reusable composition root (stage P5, `docs/architecture.md` — all of P1–P6 are closed): `core/composition.py` — builder functions (`build_llm_client`, `build_instruction_service`, `build_dataset_service`, `build_external_executor`, `build_tool_registry`, `build_agent_loop`, `build_compactor`, `build_router`, `build_cron_outcome_reporter`, `build_runner_config`, `build_conversation_manager`, `build_cron_scheduler`) plus the `ToolLimits`/`ToolStores`/`ToolServices`/`RunnerOptions` bundles — ports and configs only, no fastapi/web-Settings/Telegram; `runtime()` in web is the default assembly on top of these builders, and an alternative composition root can be built from the same builders without copying anything; `octoforge_core/__init__.py` exports the builders and the modularity ports.

Not implemented: users/authentication (`user_id` is a trusted string from the client), usage/success statistics influencing instruction search ranking, HTTP-facades for the `InstructionService`/`DatasetService`/`MemoryStore` facades (as a dedicated service), auto-injecting memory into context, an HTTP wake endpoint and service tokens for cron (standalone uses an in-process wake). Known gaps, and what is absent on purpose, are listed in `docs/limitations.md`.

## Project overview

OctoForge is a self-hosted multi-user agent platform: Python, FastAPI, async SQLAlchemy (Postgres in deployment, SQLite embedded), skills/knowledge/endpoint contracts stored in the database and retrieved by embedding search, background tasks and cron on the same dialog machinery. Details in `docs/README.md`.

## Repository layout

- `core/` — the `octoforge-core` library (src-layout): domain, ports, `composition.py` (reusable builder functions — `build_tool_registry`, `build_conversation_manager`, etc.; ports and configs only, no fastapi or web Settings), `agent/` (events/control/loop/router/prompts/runner), `tools/` (framework only: base/registry/errors; tool implementations live in `tools.py` inside the domain modules), `tasks/` (api/models/store/tools — assembled whole by the 2026-07-27 boundary audit: domain in api.py, TaskRow ORM in models.py, SQL store next to the port), `llm/` (events/openai/embeddings/local_embeddings/reranker/http_reranker — the `EmbeddingClient` and `RerankerClient` ports, a local sentence-transformers backend, an HTTP reranker backend), `db/` (framework only after the 2026-07-27 audit: base/engine/migrations — the dialogs/messages tables and stores moved to the new `dialogs/` module (api/models/store), the tasks table and SQL store into `tasks/`; migrations stay ONE chain per database on purpose — history is global and linear, and cross-module migrations exist; per-module chains belong only to modules with their own database, like telegram/invites), `instructions/` (the instructions module: api/models/store/ranking/local/registry/tools), `datasets/` (the datasets module: api/models/validation/store/ranking/service/tools), `memory/` (the thin memory module: api — the Memory DTO for the admin console; tools), `context/` (the context module: api/models/store/compactor/prompts/tools — narrative compaction and archive reads), `cron/` (the cron module: api/models/store/scheduler/waker/tools), `search/` (the `SearchProvider` port plus `SerperSearchProvider` and tools), `net/` (the SSRF guard, the external-call executor, tools incl. `endpoint_get`). Never imports fastapi; sqlalchemy appears only in `db/` and the SQL stores (`dialogs/store.py`, `instructions/store.py`, `datasets/store.py`, `context/store.py`, `cron/store.py`).
- `web/` — the `octoforge-web` application (src-layout): the FastAPI wrapper, `api/` (dialog/cron/sse/schemas), `prompts.py` (`FilePromptProvider`), `telegram/` (the Telegram surface adapter: models/client/bridge/poller, `admin.py` — the admin tool, `invites/` — invites on a separate database, `__main__` — standalone startup with no HTTP API), static assets, the composition root in `main.py` (a shared `runtime()` for both web and standalone). Depends on `octoforge-core`.
- Root: `Makefile`, `README.md`, `LICENSE`, `CONTRIBUTING.md`, `.env.example`, `docs/`, `.github/`.

- the operator console (stage H): a cross-user read model in core (`admin/api.py` — `AdminReadModel` Protocol, `Page[T]`, `DialogOverview`, `MessageRecord`, `Totals`; `admin/store.py` — SELECT+count only, row→DTO mappings mirroring each module's private converters) plus `web/api/admin.py` (paginated listings for dialogs/messages/tasks/cron/instructions/datasets/records/memories/summaries and actions that reuse `CronStore.set_enabled`/`delete_for_user`, `TaskStore.delete`, `MemoryStore.delete`, `InstructionService.publish`/`delete`) and a single static page `static/admin.html`; authentication is HTTP Basic for the whole surface except the health probes (`web/auth.py`, middleware in `create_app`; PBKDF2 hash written `pbkdf2_sha256:iterations:salt:digest` — `:` because docker compose interpolates `$` in `.env`; an empty hash means 503, never open; `logging.getLogger("httpx")` is pinned to WARNING because the Bot API URL carries the token and this process runs the bot);

## Build and test commands

- `make quickstart` — first run from a fresh clone: `tools/quickstart.py` writes `.env` (operator password printed once, Fernet key, LLM endpoint; an existing `.env` is validated, never overwritten), then the local compose overlay comes up (`docker-compose.local.yml`: project `octoforge-quickstart`, image `octoforge:quickstart` built with `CORE_EXTRAS=postgres` so no torch, no Caddy, `127.0.0.1:8000`). `make quickstart-logs` / `make quickstart-down` to follow and stop it
- `make bench` — `tools/bench_latency.py`: the real stack against a scripted LLM (framework overhead, delta delivery, concurrent tools, concurrent exchanges). Its numbers are quoted in README — update both together
- `make install` — create `.venv` and install both projects editable with dev dependencies
- `make upgrade` — refresh an existing `.venv` to what CI installs (CI resolves everything fresh every run, `install` keeps already-satisfied deps); reach for it when `make check` fails locally on code CI accepts
- `make check` — ruff (lint + format check) → mypy strict → pytest, for both projects
- `make lint` / `make typecheck` / `make test` / `make format` — the individual steps
- `make db-up` / `make db-down` / `make db-psql` — the compose Postgres service (`postgres:18-alpine` on `127.0.0.1:5432`; its init script creates `octoforge_telegram`, `octoforge_test`, `octoforge_dev` alongside `octoforge`). Point a local run at `octoforge_dev`, never at the deployment database
- `make test-pg` — `core/tests/test_postgres_stores.py` against that service; `make check` skips it for lack of `OF_TEST_DATABASE_URL`. The fixture drops the `public` schema, so the URL must name a database containing "test" (guarded)
- `make run` — uvicorn with autoreload (needs `.env` with `OF_LLM_API_KEY`)
- `make run-telegram` — Telegram bot only, no HTTP API (long polling, no port opened; needs `OF_TELEGRAM_BOT_TOKEN`)

ruff/mypy/pytest configs live in `core/pyproject.toml` and `web/pyproject.toml` respectively. Both checkers are capped there (`ruff>=0.16,<0.17`, `mypy>=2.3,<3`): a ruff minor bump stabilizes preview rules (PLR0917 in 0.16) and flips both lint errors and `noqa` usefulness, a mypy major changes inference — so an unbounded range lets CI and a local `.venv` disagree on unchanged code. Bump a cap deliberately, with the fallout in the same change.

## Code conventions

Mandatory across all project code:

1. **UTC everywhere** — every date is timezone-aware UTC. Time comes only from the `utc_now()` helper (`octoforge_core/time.py`); naive datetimes are forbidden. On SQLite, a `TypeDecorator` forces UTC on both read and write.
2. **Full typing** — annotations on every function (arguments and return value) and class attribute. Enforced by the ruff `ANN` ruleset plus mypy strict. `Any` is only allowed inside containers (`dict[str, Any]` at the JSON boundary); a bare `Any` in an annotation is forbidden (ANN401).
3. **Objects, not dicts** — data travels in domain objects (dataclass/pydantic) and ORM models. A `dict` is only allowed right at the boundary (JSON in/out) and is immediately validated into an object.
4. **Enumerations as Enum** — statuses, kinds, roles, and the like are declared via `StrEnum`; the enum's value is what's stored in the database.
5. **No magic values** — meaningful string and numeric literals are named constants or config; limits live in config. HTTP status codes in tests go through `HTTPStatus`.
6. **Tests ship with the change** — a feature or fix without tests isn't considered done. pytest + pytest-asyncio; external systems (LLM, HTTP) are mocked.
7. **Clean architecture** — layers: the `core/` library (domain, services, Protocol ports + adapters) → the `web/` application (FastAPI adapters). Dependencies point inward only: the library never imports fastapi; external clients reach services through Protocol ports.
8. **Lint before tests** — check order: `ruff check` → `ruff format --check` → `mypy` → `pytest`. One command: `make check`.
9. **Complexity limits** — ruff: `C901` (cyclomatic complexity ≤ 10), `PLR0915` (≤ 50 statements), `PLR0911` (≤ 6 returns). Exceeding a limit means splitting the function by responsibility, not disabling the rule.
10. **Core and web stay separate** — physically separate projects: `core/` and `web/`. Web is a thin adapter; all logic lives in the library.
11. **DI (Dependency Injection)** — dependencies arrive from outside: via the constructor, parameters, or `Depends` at the web layer. Constructing dependencies inside a method is forbidden; the object graph is assembled in exactly one place (the composition root: `web/src/octoforge_web/main.py` and the `core/composition.py` builders).
12. **Languages** — commit messages, docstrings, and code comments are English. `README.md` (and anything it links to) is English, aimed at a mass GitHub audience — it's the project's public storefront, not internal documentation. This file is English too, since AI coding-agent guidance conventionally lives in English. Everything else — conversation with the user, `docs/`, any other documentation — follows whatever language the user asks for; don't default to a fixed one.
13. **Communication style** — structure your responses clearly and keep the level of detail medium: enough to be useful, not exhaustive. Always respond in whatever language the user is using in that conversation.
14. **Migrations are append-only** — a `PreToolUse` hook (`.claude/settings.json`) blocks edits to any Alembic migration file already committed to git HEAD. Add a new migration file instead of editing an old one. **Write them dialect-neutrally**: `sa.false()`/`sa.true()` rather than `sa.text('0')` for boolean defaults (Postgres rejects an integer default for a boolean), and both `sqlite_where=` and `postgresql_where=` on a partial index. The pre-2026-07-25 chain violates this, which is why a fresh non-SQLite database is created from the models and stamped at head instead of replaying it (`db/engine.py:_create_and_stamp`). A new model module must be imported in **both** `db/engine.py` and `db/migrations/env.py`, or `create_all` misses its table and autogenerate proposes dropping it.

## Workflow rules

- **Git commits only with the user's explicit permission.** Ask every time before `git commit` and any other git mutation (push, reset, rebase, etc.). The same holds for `gh` when authenticated: creating a release, editing repo settings, and touching issues/PRs are equally consequential — being authenticated is not standing permission, ask first.
- **Documentation updates ship with the code.** Every logic change is written into the matching page under `docs/` in the same change (and into this file too, whenever conventions, structure or commands change). The rules for those pages are `docs/CONVENTIONS.md`: current state only, no history, code anchors per page — and `make check` runs `tools/check_docs.py`, which fails when a documented path or link no longer resolves.
- **`AGENTS.md` and `CLAUDE.md` stay in sync.** Whenever one gets a conventions/structure/commands/language update, apply the same update to the other before considering the change done.
- **Plan before touching subtle areas.** Changes to `agent/router.py`, `agent/runner.py`, `cron/`, or `context/` (compaction) have non-obvious invariants (branch reconstruction, watermarks, the pull model) — use plan mode first. A one-file, obviously-scoped fix doesn't need it.
- **No stop-the-world: one event loop serves every dialog.** The whole app is a single asyncio process — any code that blocks the loop freezes ALL users at once, not just the current dialog. On EVERY task, ask two questions about the code path you're adding: (1) does it run on the event loop, and (2) does its cost grow with data (record count, history length, users)? If it can exceed ~10 ms at target scale (~10k instruction records, years-long dialogs, many users), it must not run inline: vectorize it (numpy) and/or move it to `asyncio.to_thread`. Mind the GIL when off-loading — one long C call over Python objects (e.g. `np.asarray` on a list of tuples) holds the GIL for its whole run and stalls the loop even from a worker thread; chunk such conversions so the interpreter can switch threads (see `instructions/ranking.py`). Never hold a lock shared across dialogs over DB/network awaits (memoized per-key init instead — see `ConversationManager`), and never let a queued command be the only path for a latency-critical action (cancel bypasses the actor inbox). Measured cases and fixes: `docs/guides/performance.md`; the pure-Python cosine loop was an 847 ms full-process freeze per search at 10k records.
- **Parallelize once the plan is set.** Tests and the matching `docs/` update don't have to wait for the implementation to land. Once a plan fixes the interfaces and behavior, write the tests, the docs update, and the implementation in parallel instead of serializing them.
- **Definition of done.** A change isn't done until `make check` passes — run it yourself and show the output, don't just assert success, and don't take a subagent's summary of its own work as confirmation — look at the actual diff or output.
- **Mocked tests aren't proof of behavior.** `make check` mocks the LLM and HTTP (convention 6) — a green run doesn't prove the agent loop, SSE stream, or Telegram bridge actually works end to end. For changes touching `agent/loop.py`, SSE delivery, or `telegram/`, also exercise it live (`make run` plus a real message, or the `/verify` skill) and look at the raw output, not just an assertion that it should work.
- **Get a second opinion before shipping.** For a non-trivial diff, run a review pass (e.g. `/code-review`) in a fresh context in addition to `make check` — a green test suite doesn't catch every logic gap.
- **Choose subagent capability by task, don't default to the strongest.** A **fast** tier for mechanical grep/exploration on a known pattern; a **standard** tier for implementation, tests, review, and most exploration; a **heavy** tier only for genuinely hard architectural tradeoffs or arbitrating conflicting reviews. Note which tier you used when reporting back. (Deliberately tool-agnostic here — this file isn't Claude-specific; see `CLAUDE.md` for the concrete model names in this harness.)
- **On compaction, keep the essentials.** When a long session gets compacted, always preserve the list of modified files, any `OF_*` env vars or migration ids touched, and the last `make check` result.
