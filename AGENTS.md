## Project status

An event loop with a dialog actor (process model + LLM router), SQLite persistence, and background task-processes all work. Implemented:

- a monorepo of two projects: the `core/` library (`octoforge-core`) and the `web/` application (`octoforge-web`) — each with its own `pyproject.toml`, dependencies, and tests;
- the loop as an event stream: `AgentLoop.stream(history, control, context) -> AsyncIterator[LoopEvent]` — tokens, tool calls, final, cancellation; eager tool execution as soon as arguments are ready (`ToolCallStarted`/`Ready`/`Broken` events in the stream, concurrent execution, history strictly in call order, fallback to start-after-`StreamFinished`) and a stream idle watchdog (`stream_idle_timeout`, config `OF_LLM_STREAM_IDLE_TIMEOUT_SECONDS`); see `docs/streaming.md`;
- run control: `LoopControl` — cancellation only, preserving the partial answer (the injection channel was retired by the pull model: a process branch re-reads the narrative on every iteration);
- the dialog process model (stage E): the actor-broker `ConversationRunner` owns the narrative (user messages + process finals + system notes; only this is persisted), the processes (fg/bg, in memory), and result delivery; every process is backed by a task (`process.id == task.id`: ANSWER — a reply to a user message, RUN — task_create/cron); a branch = `[system] + a compactor snapshot of the narrative + a private working suffix` and re-reads the narrative on every `IterationStarted` (pull model instead of injections; no change — byte-identical); a narrative watermark — user messages that went unseen at finalization time are re-routed; broadcast — foreground events plus `ProcessSuspended`/`ProcessCompleted` markers; `ConversationManager` — runners keyed by `(user_id, channel)` (get-or-create), built via `RunnerConfig` (prompts through the `PromptProvider` port); graceful shutdown — `ConversationManager.stop_all()` from `runtime()` (web): `runner.stop()` cancels and awaits the actor and pump tasks and stops its own dialog's background compaction;
- core prompts behind the `PromptProvider` port (`agent/prompts.py`; default is `StaticPromptProvider` over hardcoded constants, the router prompt was moved out of `LLMRouter` into the provider); the web layer adds `FilePromptProvider` (`OF_SYSTEM_PROMPT_SOURCE`/`OF_ROUTER_PROMPT_SOURCE`, `file:/path` format, re-read on every `get`, falls back to the built-in default);
- LLM router (`agent/router.py`): the `MessageRouter` port (a batch of `RouteOp`: INJECT/START_NEW/CANCEL), `LLMRouter` — a one-shot `complete()` call with the `route(ops)` tool, a timeout (`OF_ROUTER_TIMEOUT_SECONDS`), op validation, a fallback (INJECT, not START_NEW, when a foreground process is active); the LLM call is skipped when the process list is empty (deterministic START_NEW); a deterministic guardrail: a batch containing INJECT drops every START_NEW (an injection must never spin the question off into the background); a process-count guardrail (`OF_MAX_PROCESSES`) lives in the actor; "bring back task X" is routed as START_NEW (there is no PROMOTE op — a fresh process sees the whole narrative); router-side skill presearch (searches + `PresearchPort`) was removed on 2026-07-21 — scenarios only reach the context through `instruction_search` during a run (see `docs/instructions.md`);
- persistence: async SQLAlchemy + SQLite, the `db/` package (Base + `UTCDateTime`, ORM models for dialogs/messages/tasks, engine/session factories, repositories); schema via Alembic (`bootstrap_schema`: upgrades to head at startup inside an explicit migration-transaction commit; pre-Alembic databases are stamped at the baseline and caught up — ALTER migrations add columns conditionally; `create_all` is the fallback used by tests); message `seq` is assigned atomically by a subquery inside the INSERT;
- background tasks are background actor processes (stage E): `TaskKind` (RUN — task_create/cron; ANSWER — the internal mechanics of replying to a user message, invisible to tools), `TaskStatus` (+CANCELLED — a terminal state for both processes and `cron_jobs.last_status`), the `TaskStore` port (`tasks/store.py`: add/get/list/mark_done/mark_failed/mark_cancelled/delete/list_orphaned/list_undelivered/mark_delivered — task rows are kept forever; `delivered_at` records delivery of the result to the transport, `list_undelivered` = DONE/FAILED with `delivered_at IS NULL`; a final is linked to its task via `messages.task_id`, migration `d1e5f9a3b247`; a task's parent link lives in `input`: `{cron_job_id, fired_at}` for cron fires, `{source_message_id}` for answer tasks (the id of the user's question message; `ChatMessage.id` — the DB row id, pure DB metadata, excluded from equality)); spawning goes through the `TaskSpawner` port, stopping through the `TaskDeleter` port (both in `tasks/spawner.py`, bound implementations live on the actor; a tool cannot delete its own owning task — rejected via `ToolContext.owner_task_id`); tools `task_create`/`task_list`/`task_delete` (`task_list` shows RUN tasks that are in flight or awaiting delivery — delivered and answer tasks are hidden; `task_delete` only stops a task — the row stays CANCELLED); result delivery with no LLM involved: a background task's final is placed in the outbox (`_pending_deliveries`) and goes out whole (DONE → TextDelta + Finished, FAILED → Failed) once the foreground is free **and at least one subscriber is attached** (a broadcast into zero queues reaches nobody, so stamping it delivered would lose the result for good — the outbox waits and drains on the next `subscribe()`, which enqueues a `_Flush` command; live stream events are never replayed, only the outbox is); a foreground final has already been streamed live — only `delivered_at` gets set; a limit-exceeded rejection is a templated broker notice delivered the same outbox way; startup recovery — `ConversationManager.recover_interrupted()`, called from `runtime()` before the scheduler starts: PENDING/RUNNING → restarted as a background process (`restart_task`, queue mode; exceeding the limit → mark_failed plus a delivered Failed); a cron-tagged outcome goes through `TaskOutcomeListener` once the restarted process finalizes; undelivered results are re-delivered through the normal `_ProcessTerminated` path (`request_result_delivery`, idempotent on `delivered_at`); the current date/time is an envelope on the branch's last message (`_with_date_envelope`: the system prompt stays byte-stable for prefix caching, the narrative/persisted copy is untouched; see `docs/prompt-caching.md`);
- tools: `Tool`/`ToolSpec`/`ToolContext(user_id, channel, dialog_id, task_spawner?, task_deleter?, owner_task_id?)`/`ToolRegistry` (no `SkillOrigin` — removed; `specs(context?)` is a shared duck-typed visibility hook: a tool with an optional `visible_to(context) -> bool` attribute only appears in the tool list when it returns True; without the attribute, it's always visible); the `tools/` package is framework only (base/registry/errors) — implementations live in the domain modules: `tasks/tools.py` (`task_create` — a background task without `schedule`, a cron job with `schedule` (delegates to `create_job` from `cron/tools.py`: dedupes identical jobs, `one_shot`, timezone defaults to UTC); `task_list` — two sections, dialog tasks and the user's cron jobs, both with a prompt preview (`prompt_preview`, truncated to `PROMPT_PREVIEW_CHARS`); `task_delete` — stops a task (the row stays CANCELLED), and also handles deleting cron jobs), `cron/tools.py` (`cron_pause`/`cron_resume` plus the domain `create_job`/`format_job`), `memory/tools.py` (`memory_store`/`memory_search`/`memory_delete`), `datasets/tools.py` (`data_put`/`data_query`/`data_forget`), `context/tools.py` (`history_search`), `search/tools.py` (`web_search` through the `SearchProvider` port; the default is `SerperSearchProvider` for serper.dev, gated on `OF_SERPER_TOKEN`), `net/tools.py` (`http_request`, `external_call`), `instructions/tools.py` (`instruction_search` — answers in two blocks (instructions with FULL scenario text and an `id`, then dataset descriptors), a `type` filter, no score, a single top-k plus a character cap with a truncation note; `instruction_save` — a private record owned by the session's user; `instruction_delete` — own records only, by id);

The plan lives in `docs/design.md`.

## Project overview

OctoForge is a multi-user LLM agent: Python, FastAPI, SQLAlchemy (async, SQLite), tools as executable Jinja templates, knowledge in the database, background tasks with notifications. Details in `docs/design.md`.

## Code conventions

Mandatory across all project code:

1. **UTC everywhere** — every date is timezone-aware UTC. Time comes only from the `utc_now()` helper (`octoforge_core/time.py`); naive datetimes are forbidden. On SQLite, a `TypeDecorator` forces UTC on both read and write.
2. **Full typing** — annotations on every function (arguments and return value) and class attribute. Enforced by the ruff `ANN` ruleset plus mypy strict. `Any` is only allowed inside containers (`dict[str, Any]` at the JSON boundary); a bare `Any` in an annotation is forbidden (ANN401).
3. **Objects, not dicts** — data travels in domain objects (dataclass/pydantic) and ORM models. A `dict` is only allowed right at the boundary (JSON in/out) and is immediately validated into an object.
4. **Enumerations as Enum** — statuses, kinds, roles, and the like are declared via `StrEnum`; the enum's value is what's stored in the database.
5. **No magic values** — meaningful string and numeric literals are named constants or config; limits live in config. HTTP status codes in tests go through `HTTPStatus`.
6. **Tests ship with the change** — a feature or fix without tests isn't considered done. pytest + pytest-asyncio; external systems (LLM, HTTP) are mocked.
7. **Clean architecture** — layers: the `core/` library (domain, services, Protocol ports + adapters) → the `web/` application (FastAPI adapters). Dependencies point inward only: the library never imports fastapi; external clients reach services through Protocol ports.
8. **Lint before tests** — check order: `ruff check` → `ruff format --check` → `mypy` → `pytest`. One command: `make check`.
9. **Complexity limits** — ruff: `C901` (cyclomatic complexity ≤ 10), `PLR0915` (≤ 50 statements), `PLR0911` (≤ 6 returns). Exceeding a limit means splitting the function by responsibility, not disabling the rule.
10. **Core and web stay separate** — physically separate projects: `core/` and `web/`. Web is a thin adapter; all logic lives in the library.
11. **DI (Dependency Injection)** — dependencies arrive from outside: via the constructor, parameters, or `Depends` at the web layer. Constructing dependencies inside a method is forbidden; the object graph is assembled in exactly one place (the composition root: `web/src/octoforge_web/main.py` and the `core/composition.py` builders).
12. **Languages** — commit messages, docstrings, and code comments are English. `README.md` (and anything it links to) is English, aimed at a mass GitHub audience — it's the project's public storefront, not internal documentation. This file is English too, since AI coding-agent guidance conventionally lives in English. Everything else — conversation with the user, `docs/`, any other documentation — follows whatever language the user asks for; don't default to a fixed one.
13. **Communication style** — structure your responses clearly and keep the level of detail medium: enough to be useful, not exhaustive. Always respond in whatever language the user is using in that conversation.
14. **Migrations are append-only** — a `PreToolUse` hook (`.claude/settings.json`) blocks edits to any Alembic migration file already committed to git HEAD. Add a new migration file instead of editing an old one.

## Workflow rules

- **Git commits only with the user's explicit permission.** Ask every time before `git commit` and any other git mutation (push, reset, rebase, etc.). The same holds for `gh` when authenticated: creating a release, editing repo settings, and touching issues/PRs are equally consequential — being authenticated is not standing permission, ask first.
- **Documentation updates ship with the code.** Every change to logic, and every new idea, is written into `docs/design.md` (and into this file too, whenever conventions, structure, or commands change) in the same change.
- **`AGENTS.md` and `CLAUDE.md` stay in sync.** Whenever one gets a conventions/structure/commands/language update, apply the same update to the other before considering the change done.
- **Plan before touching subtle areas.** Changes to `agent/router.py`, `agent/runner.py`, `cron/`, or `context/` (compaction) have non-obvious invariants (branch reconstruction, watermarks, the pull model) — use plan mode first. A one-file, obviously-scoped fix doesn't need it.
- **Parallelize once the plan is set.** Tests and the matching `docs/design.md` update don't have to wait for the implementation to land. Once a plan fixes the interfaces and behavior, write the tests, the docs update, and the implementation in parallel instead of serializing them.
- **Definition of done.** A change isn't done until `make check` passes — run it yourself and show the output, don't just assert success, and don't take a subagent's summary of its own work as confirmation — look at the actual diff or output.
- **Mocked tests aren't proof of behavior.** `make check` mocks the LLM and HTTP (convention 6) — a green run doesn't prove the agent loop, SSE stream, or Telegram bridge actually works end to end. For changes touching `agent/loop.py`, SSE delivery, or `telegram/`, also exercise it live (`make run` plus a real message, or the `/verify` skill) and look at the raw output, not just an assertion that it should work.
- **Get a second opinion before shipping.** For a non-trivial diff, run a review pass (e.g. `/code-review`) in a fresh context in addition to `make check` — a green test suite doesn't catch every logic gap.
- **Choose subagent capability by task, don't default to the strongest.** A **fast** tier for mechanical grep/exploration on a known pattern; a **standard** tier for implementation, tests, review, and most exploration; a **heavy** tier only for genuinely hard architectural tradeoffs or arbitrating conflicting reviews. Note which tier you used when reporting back. (Deliberately tool-agnostic here — this file isn't Claude-specific; see `CLAUDE.md` for the concrete model names in this harness.)
- **On compaction, keep the essentials.** When a long session gets compacted, always preserve the list of modified files, any `OF_*` env vars or migration ids touched, and the last `make check` result.
