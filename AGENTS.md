# AGENTS.md

> Guidance for AI coding agents working in this repository.

## Project status

Событийная петля с актором диалога (процессная модель + LLM-роутер), персистом в SQLite и фоновыми задачами-процессами работает. Реализовано:

- монорепо из двух проектов: библиотека `core/` (`octoforge-core`) и web-приложение `web/` (`octoforge-web`) — у каждого свой `pyproject.toml`, зависимости и тесты;
- петля как поток событий: `AgentLoop.stream(history, control, context) -> AsyncIterator[LoopEvent]` — токены, вызовы тулов, финал, отмена; eager-исполнение тулов по готовности аргументов (события `ToolCallStarted`/`Ready`/`Broken` в стриме, конкурентный запуск, история строго в порядке вызовов, fallback на старт после `StreamFinished`) и idle-watchdog стрима (`stream_idle_timeout`, конфиг `OF_LLM_STREAM_IDLE_TIMEOUT_SECONDS`); см. `docs/streaming.md`;
- управление прогоном: `LoopControl` — только отмена с сохранением частичного ответа (канал инъекций упразднён pull-моделью: ветка процесса перечитывает нарратив на каждой итерации);
- процессная модель диалога (этап E): актор-брокер `ConversationRunner` владеет нарративом (user-сообщения + финалы процессов + служебные заметки; только он персистится), процессами (fg/bg, в памяти) и доставкой результатов; каждый процесс подкреплён задачей (`process.id == task.id`: ANSWER — ответ на сообщение пользователя, RUN — task_create/крон), ветка = `[system] + снапшот нарратива от компактора + приватный рабочий суффикс` и перечитывает нарратив на каждом `IterationStarted` (pull-модель вместо инъекций; без изменений — байт-идентична), водяная метка нарратива — неувиденные user-сообщения при финализации уходят на повторный роутинг; broadcast — события форграунда + маркеры `ProcessSuspended`/`ProcessCompleted`; `ConversationManager` — runners по `(user_id, channel)` (get-or-create), конструктор через `RunnerConfig` (промпты — через порт `PromptProvider`); graceful shutdown — `ConversationManager.stop_all()` из `runtime()` (web): `runner.stop()` отменяет и дожидается actor- и pump-задач и гасит фоновую компакцию своего диалога;
- промпты ядра за портом `PromptProvider` (`agent/prompts.py`; дефолт — `StaticPromptProvider` поверх вшитых констант, роутерный промпт вынесен из `LLMRouter` в провайдер); web-слой добавляет `FilePromptProvider` (`OF_SYSTEM_PROMPT_SOURCE`/`OF_ROUTER_PROMPT_SOURCE`, формат `file:/path`, перечитывание на каждый get, fallback на вшитый дефолт);
- LLM-роутер (`agent/router.py`): порт `MessageRouter` (пакет `RouteOp`: INJECT/START_NEW/CANCEL), `LLMRouter` — one-shot `complete()` с tool `route(ops)`, таймаут (`OF_ROUTER_TIMEOUT_SECONDS`), валидация ops, фолбэк (при активном форграунде — INJECT, не START_NEW); при пустом списке процессов LLM-вызов пропускается (детерминированный START_NEW); детерминированный guardrail: пакет с INJECT теряет все START_NEW (инъекция не уводит вопрос в фон); guardrail лимита процессов (`OF_MAX_PROCESSES`) в акторе; «верни задачу X» маршрутизируется как START_NEW (опа PROMOTE нет — свежий процесс видит весь нарратив); пре-поиск скилов роутером (searches + `PresearchPort`) удалён 2026-07-21 — сценарии попадают в контекст только через `instruction_search` в прогоне (см. `docs/instructions.md`);
- персист: SQLAlchemy async + SQLite, пакет `db/` (Base + `UTCDateTime`, ORM-модели dialogs/messages/tasks, фабрики engine/session, репозитории); схема — Alembic (`bootstrap_schema`: upgrade до head при старте с явным commit'ом транзакции миграций, pre-Alembic БД штампуется на baseline и догоняется — ALTER-миграции добавляют колонки условно; `create_all` — fallback и тесты); `seq` сообщений присваивается атомарно подзапросом в INSERT;
- фоновые задачи = фоновые процессы актора (этап E): `TaskKind` (RUN — task_create/крон; ANSWER — внутренняя механика ответа на сообщение пользователя, в тулах не видна), `TaskStatus` (+CANCELLED — терминал процессов и `cron_jobs.last_status`), порт `TaskStore` (`tasks/store.py`: add/get/list/mark_done/mark_failed/mark_cancelled/delete/list_orphaned/list_undelivered/mark_delivered — строки задач хранятся вечно; `delivered_at` фиксирует доставку результата в транспорт, `list_undelivered` = DONE/FAILED с `delivered_at IS NULL`; финал связывается с задачей через `messages.task_id`, миграция `d1e5f9a3b247`; родительская связь задачи — в `input`: `{cron_job_id, fired_at}` у крон-выстрелов, `{source_message_id}` у answer-задач (id user-сообщения-вопроса; `ChatMessage.id` — id строки в БД, чистые DB-метаданные, из равенства исключён)); спавн — порт `TaskSpawner`, остановка — порт `TaskDeleter` (оба в `tasks/spawner.py`, bound-реализации в акторе; самоудаление из собственного прогона тул отклоняет через `ToolContext.owner_task_id`); тулы `task_create`/`task_list`/`task_delete` (`task_list` — RUN-задачи в полёте или ждущие доставки, доставленные и answer-задачи скрыты; `task_delete` только останавливает — строка остаётся CANCELLED), доставка результата без LLM: финал фоновой задачи встаёт в outbox (`_pending_deliveries`) и уходит целиком (DONE → TextDelta + Finished, FAILED → Failed), когда форграунд свободен, финал форграунда уже отстримлен живьём — только проставляется `delivered_at`; отказ по лимиту — шаблонное уведомление брокера тем же outbox-путём; startup-recovery — `ConversationManager.recover_interrupted()` из `runtime()` до старта планировщика: PENDING/RUNNING → перезапуск фоновым процессом (`restart_task`, queue-режим; превышение лимита → mark_failed + доставка Failed), cron-tagged исход — через `TaskOutcomeListener` после финализации перезапущенного процесса, недоставленные результаты редоставляются штатным путём `_ProcessTerminated` (`request_result_delivery`, идемпотентно по `delivered_at`); текущие дата/время — конвертом на последнем сообщении ветки (`_with_date_envelope`: системный промпт байт-стабилен для prefix-cache, нарратив/персист — чистая копия; см. `docs/prompt-caching.md`);

- компакция контекста диалога (дизайн — `docs/context.md`): обособленный пакет `context/` (граница `api.py` — порты `ContextCompactor`/`SummaryStore`/`MessageArchive`, DTO `DialogueSummary`/`ArchivedMessage`/`ArchiveFilter`; `SqlAlchemySummaryStore` реализует оба стора — таблица `dialog_summaries` + read-only чтение архива `messages`); ветка процесса собирается компактором из `RunnerConfig.compactor` (обязательный; `NoopContextCompactor` — дефолт в тестах): блок тем (одно rolling-саммари диалога system-сообщением) + горячий хвост (`seq > max(seq_to)`, дословно, из нарратива актора); переполнение хвоста (`OF_CONTEXT_HOT_MAX_CHARS`, символы) или токенный порог (`OF_MODEL_CONTEXT_TOKENS` − `OF_CONTEXT_BUFFER_TOKENS` по usage последнего ответа; usage провайдера персистится на assistant-сообщениях — колонки `prompt_tokens`/`completion_tokens`, `complete()` возвращает DTO `Completion(message, usage)`) триггерит фоновую asyncio-компакцию `LlmContextCompactor` — старейшие сообщения хвоста (до `OF_CONTEXT_COMPACT_TARGET_CHARS`) одним one-shot `complete()` в запись `dialog_summaries` с тегами тем; guard «одна компакция на диалог», фейл = warning-лог (диалог не страдает), отмена компакции своего диалога при `stop()` runner'а (`aclose(dialog_id)` — компактор shared на менеджер); суммаризация — rolling merge (промпт обновляет предыдущее саммари, `replace_for_dialog` держит одну запись на диалог); реактивный путь: `ContextOverflowError` → `compact_now` синхронно → пересборка ветки → один повтор прогона; срез сегмента — только между сообщениями и никогда внутри salvaged-пары (`INTERRUPTED_NOTE`); тул `history_search` (LIKE-подстрока по архиву текущего диалога, фильтры темы/дат, лимиты `OF_HISTORY_SEARCH_DEFAULT_LIMIT`/`OF_HISTORY_SEARCH_MAX_LIMIT`); методика поиска по истории — системный скил `history_lookup`;
- переиспользуемый composition root (этап P5, `docs/modularity.md` — все этапы P1–P6 закрыты): `core/composition.py` — builder-функции сборки (`build_llm_client`, `build_instruction_service`, `build_dataset_service`, `build_external_executor`, `build_tool_registry`, `build_agent_loop`, `build_compactor`, `build_router`, `build_cron_outcome_reporter`, `build_runner_config`, `build_conversation_manager`, `build_cron_scheduler`) + бандлы `ToolLimits`/`ToolStores`/`ToolServices`/`RunnerOptions`; только порты и конфиги, без fastapi/web-Settings/Telegram; `runtime()` в web — дефолтная сборка поверх builder'ов, сторонний корень собирается из них же без копирования; `octoforge_core/__init__.py` экспортирует builder'ы и порты модульности;

Не реализовано: пользователи/аутентификация (user_id — доверенная строка от клиента), влияние usage/success-статистики на ранг поиска инструкций и http-реализация фасадов `InstructionService`/`DatasetService`/`MemoryStore` (выделенный сервис), автоинъекция памяти в контекст, HTTP wake endpoint и служебные токены для крона (в standalone — in-process wake). План — `docs/design.md`.

## Project overview

OctoForge — мультипользовательский LLM-агент: Python, FastAPI, SQLAlchemy (async, SQLite), тулы на исполняемых Jinja-шаблонах, знания в БД, фоновые задачи с уведомлениями. Детали — `docs/design.md`.

## Repository layout

- `core/` — библиотека `octoforge-core` (src-layout): домен, порты, `composition.py` (переиспользуемые builder'ы сборки — `build_tool_registry`, `build_conversation_manager` и др.; только порты/конфиги, без fastapi и web-Settings), `agent/` (events/control/loop/router/prompts/runner), `tools/` (фреймворк: base/registry/errors; реализации тулов — `tools.py` в доменных модулях), `tasks/` (models/store/spawner/errors/tools), `llm/` (events/openai/embeddings/local_embeddings/reranker/http_reranker — порты `EmbeddingClient` и `RerankerClient`, локальный бэкенд на sentence-transformers, HTTP-бэкенд реранка), `db/` (base/models/engine/repositories), `instructions/` (модуль инструкций: api/models/store/ranking/local/registry/tools), `datasets/` (модуль датасетов: api/models/validation/store/ranking/service/tools), `memory/` (модуль памяти: api/models/store/tools), `context/` (модуль контекста: api/models/store/compactor/prompts/tools — компакция нарратива и чтение архива), `cron/` (модуль крон-задач: api/models/store/scheduler/waker/tools), `search/` (порт `SearchProvider` + SerperSearchProvider + tools), `net/` (SSRF-гвард, исполнитель внешних вызовов, tools). Не импортирует fastapi; sqlalchemy — только в `db/` и SQL-сторах (`db/repositories.py`, `instructions/store.py`, `datasets/store.py`, `memory/store.py`, `context/store.py`, `cron/store.py`).
- `web/` — приложение `octoforge-web` (src-layout): FastAPI-обёртка, `api/` (dialog/cron/sse/schemas), `prompts.py` (`FilePromptProvider`), `telegram/` (адаптер поверхности Telegram: models/client/bridge/poller, `admin.py` — админский тул, `invites/` — инвайты на отдельной БД, `__main__` — standalone-запуск без HTTP API), статика, composition root в `main.py` (общий `runtime()` для web и standalone). Зависит от `octoforge-core`.
- Корень: `Makefile`, `README.md`, `.env.example`, `docs/`.

## Build and test commands

- `make install` — создать `.venv` и поставить оба проекта editable с dev-зависимостями
- `make check` — ruff (lint + format check) → mypy strict → pytest для обоих проектов
- `make lint` / `make typecheck` / `make test` / `make format` — шаги по отдельности
- `make run` — uvicorn с автоперезагрузкой (нужен `.env` с `OF_LLM_API_KEY`)
- `make run-telegram` — только Telegram-бот, без HTTP API (long polling, порт не открывается; нужен `OF_TELEGRAM_BOT_TOKEN`)

Конфиги ruff/mypy/pytest — в `core/pyproject.toml` и `web/pyproject.toml` соответственно.

## Code conventions

Обязательны во всём коде проекта:

1. **UTC everywhere** — все даты timezone-aware UTC. Время получаем только через хелпер `utc_now()` (`octoforge_core/time.py`); naive datetime запрещены. На SQLite — TypeDecorator, принудительно выставляющий UTC при чтении/записи.
2. **Полная типизация** — аннотации на всех функциях (аргументы и возвращаемое значение) и атрибутах классов. Контроль: ruff ruleset `ANN` + mypy strict. `Any` только внутри контейнеров (`dict[str, Any]` на JSON-границе), голый `Any` в аннотациях запрещён (ANN401).
3. **Объекты, не словари** — данные носим в доменных объектах (dataclass/pydantic) и ORM-моделях. `dict` допустим только на самой границе (JSON in/out) и сразу валидируется в объект.
4. **Перечисления — Enum** — статусы, виды, роли и т.п. объявляем через `StrEnum`; в БД хранится значение enum'а.
5. **Никакой магии** — строковые и числовые литералы со смыслом — именованные константы или конфиг; лимиты — в конфиге. В тестах HTTP-коды — через `HTTPStatus`.
6. **Тесты в том же изменении** — фича или фикс без тестов не считается сделанным. pytest + pytest-asyncio; внешние системы (LLM, HTTP) мокаем.
7. **Чистая архитектура** — слои: библиотека `core/` (домен, сервисы, порты-Protocol + адаптеры) → приложение `web/` (FastAPI-адаптеры). Зависимости только внутрь: библиотека не импортирует fastapi; внешние клиенты попадают в сервисы через Protocol-порты.
8. **Линтер перед тестами** — порядок проверки: `ruff check` → `ruff format --check` → `mypy` → `pytest`. Одна команда: `make check`.
9. **Контроль сложности** — ruff: `C901` (цикломатическая сложность ≤ 10), `PLR0915` (≤ 50 statements), `PLR0911` (≤ 6 return'ов). Превышение = дробим функцию по ответственности, а не отключаем правило.
10. **Ядро отдельно, web отдельно** — физически разные проекты: `core/` и `web/`. Web — тонкий адаптер, вся логика в библиотеке.
11. **DI (Dependency Injection)** — зависимости приходят снаружи: через конструктор, параметры или `Depends` на web-слое. Создавать зависимости внутри методов запрещено; сборка графа объектов — в одном месте (composition root: `web/src/octoforge_web/main.py` и фабрики).
12. **Языки** — общение с пользователем и вся документация (`docs/`, этот файл) — на русском. Коммиты, docstrings и комментарии в коде — на английском. Исключение: `README.md` и всё, на что он ссылается, — на хорошем английском, понятном массовому пользователю GitHub: это публичная витрина проекта, а не внутренняя документация.

## Workflow rules

- **Git-коммиты — только с явного разрешения пользователя.** Спрашивать разрешение каждый раз перед `git commit` и любой другой git-мутацией (push, reset, rebase и т.д.).
- **Документация обновляется вместе с кодом.** Каждое изменение, меняющее логику, и каждая новая идея дописываются в `docs/design.md` (а при смене конвенций, структуры или команд — и в этот файл) в том же изменении.
