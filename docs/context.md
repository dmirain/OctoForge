# Контекст диалога: уровни, компакция, поиск (дизайн)

> **Статус: дизайн (код не менялся).** Дизайн DI-компонента сжатия контекста.
> Подтверждённые решения: при переполнении горячего хвоста старые сообщения уходят
> в саммаризацию (свежий хвост нетронут); все саммари уходят в промпт целиком;
> лимит измеряется в символах (без токенизатора); суммаризация — фоновым процессом.
> Связанные доки: [design.md](design.md), [dialogs.md](dialogs.md),
> [plan.md](plan.md), [modularity.md](modularity.md); исследование компакции
> в openclaw — [openclaw-compaction.md](openclaw-compaction.md).

## Проблема

Сейчас вся история диалога (`_narrative` в акторе) целиком копируется в ветку
каждого нового процесса (`agent/runner.py:_start_new`: `[system, *narrative, trail]`).
История растёт бесконечно: токены и стоимость каждого прогона растут линейно,
качество ответов деградирует с длиной контекста. Наивное усечение (последние N
сообщений или K символов) решает рост, но теряет ранние договорённости — агент
«забывает», о чём говорили вчера. Нужна многоуровневая система: полный архив +
сжатое представление прошлого + нетронутое настоящее.

## Три уровня контекста

### Уровень 1 — архив (уже есть)

Таблица `messages`: вечная полная история диалога, «стоит условно ничего».
Источник истины. Пишется актором, как сейчас (`MessageRepository.append`,
`seq` монотонный per dialog). По архиву можно искать (см. «Поиск» ниже) — агент
способен сам найти нужное обсуждение, когда саммари недостаточно.

### Уровень 2 — темы (периодические саммаризации)

Новая таблица `dialog_summaries`:

| колонка | смысл |
|---|---|
| `id` | первичный ключ |
| `dialog_id` | владелец (как у messages) |
| `seq_from`, `seq_to` | покрытый диапазон `seq` архива |
| `topics` | JSON-список тегов тематики (1–4, ставит LLM при суммаризации) |
| `content` | сжатый текст сегмента |
| `created_at` | когда записана (UTC) |

Каждая запись — сжатый сегмент истории с разметкой тематики. **Все саммари
диалога уходят в промпт целиком** (подтверждённое решение: «пока не думаем о
слишком большом числе тем»; риск роста — в «Не входит»).

### Уровень 3 — горячий хвост

Сообщения архива с `seq > max(seq_to)` саммаризаций диалога. Граница выводится
из данных — отдельного указателя/колонки «до куда сжато» не нужно, состояние
консистентно при любом рестарте. Хвост уходит в промпт нетронутым: свежий
контекст всегда дословный.

## Поток данных

1. Каждое сообщение по-прежнему пишется в `messages` (уровень 1) и в `_narrative`.
2. Сборка ветки процесса (`_start_new`) делегируется компактору:
   `system` (с датой) → **блок тем** (все саммари: период, темы, текст; при
   отсутствии — блок пропускается) → **горячий хвост** → trail (напр. nudge
   репорт-прогона). Фоновые задачи (`BACKGROUND_TASK_PROMPT`) нарратива не видят —
   компакция их не касается.
3. Когда горячий хвост превышает лимит (`OF_CONTEXT_HOT_MAX_CHARS`, символы как
   прокси токенов ~4:1; токенизатор не заводим, честные токены — отдельная
   итерация), компактор запускает **фоновую компакцию**: самые старые сообщения
   хвоста (до целевого размера, тоже конфиг) одним LLM-вызовом превращаются в
   запись `dialog_summaries` с тегами тем. Свежий хвост не трогаем.
4. До завершения фонового прогона ветки собираются с чуть устаревшими саммари и
   хвостом чуть за лимитом — осознанная плата за отсутствие пауз в диалоге
   (альтернатива — синхронная суммаризация при сборке — отклонена).
5. Промпт суммаризации (шаблон в `context/prompts.py`): «сожми сегмент диалога;
   верни 1–4 тега тем (короткие, lowercase, нормализованные) и сжатый текст,
   сохраняющий факты, решения, договорённости, имена, числа и незакрытые задачи».

## Срез только на безопасных границах

Принцип из анализа openclaw ([openclaw-compaction.md](openclaw-compaction.md)):
точка среза выбирается так, чтобы не разорвать неделимые единицы контекста.

- **Гранулярность — целые сообщения**: срез всегда между сообщениями архива
  (`seq`), никогда внутри сообщения.
- **Tool-пары**: в нарративе их нет — он состоит из user-сообщений, финальных
  ответов и системных заметок (промежуточные assistant/tool-сообщения веток не
  персистятся), поэтому разрыв пары `assistant(tool_calls) ↔ tool_result` для
  компакции нарратива невозможен по построению. Для **будущей компакции веток
  прогонов** (см. «Не входит») правило становится обязательным: пары
  tool_call/tool_result не разрываются, срез — только между завершёнными
  итерациями; осиротевшие tool-сообщения недопустимы (API их отвергает).
- **Логические пары нарратива**: salvaged-фрагмент прерванного ответа и следующая
  за ним заметка о неполноте (`INTERRUPTED_NOTE`) срезом не разделяются — граница
  сдвигается к началу пары (обе уходят в саммари) либо к её концу (обе остаются
  в хвосте). Остальные соседние сообщения нарратива независимы и разделяются
  свободно.

## Компонент и порты (DI)

Новый обособленный пакет `octoforge_core/context/` (зеркалит
instructions/datasets/memory/cron):

- `api.py` — граница модуля:
  - `ContextCompactor` (Protocol): `assemble(dialog, history) ->
    list[ChatMessage]` — ветка процесса (темы + горячий хвост); внутри — триггер
    фоновой компакции при переполнении.
  - `SummaryStore` (Protocol): CRUD саммари, `max_seq_to(dialog_id)`, поиск для
    скилла. DTO `DialogueSummary` (JSON-friendly, как везде).
- `store.py` — `SqlAlchemySummaryStore` (таблица — собственность модуля,
  Alembic-ревизия).
- `compactor.py` — реализация по умолчанию: политика лимита, LLM-вызов
  суммаризации (`complete()`, one-shot), фоновой таск.
- `prompts.py` — шаблон промпта суммаризации.

Правила фонового запуска:

- компакция — **своя asyncio-задача внутри компактора**, не акторский процесс:
  техническая работа не должна шуметь в диалоге маркерами процессов;
- guard «одна компакция на диалог»: повторное переполнение во время прогона не
  плодит второго — следующая сборка ветки дотриггерит при необходимости;
- фейл суммаризации — warning-лог, диалог не страдает; хвост продолжает расти
  до следующего триггера (деградация мягкая, не ошибка);
- задача отменяется при остановке runner'а; runner получает компактор через
  `RunnerConfig` из composition root (DI, подменяемо как прочие порты — см.
  [modularity.md](modularity.md)).

## Поиск по архиву (уровень 1 → агент)

Саммари уже в промпте; для глубокого поиска — новый базовый скил:

- `history_search(query, topic?, date_from?, date_to?, limit?)` — LIKE-подстрока
  по `messages.content` внутри диалога (та же механика, что у `memory_search`);
  опциональный фильтр темы: совпадение по тегам `dialog_summaries` → выдача
  ограничена их seq-диапазонами. Результаты с датами/`seq`, лимиты из конфига.
- Системный промпт += правило: «если речь о ранее обсуждённом вне горячего
  хвоста — ищи по истории через history_search, не переспрашивай пользователя».
- Эмбеддинги по архиву — отдельная итерация (инфраструктура `EmbeddingClient`
  уже есть; LIKE достаточен для старта).

## Не входит (зафиксировано)

- **Эвикция runner'ов из памяти** (LRU/TTL) — смежная задача качества
  ([quality-audit.md](quality-audit.md), волна 3), решается отдельно.
- Честный подсчёт токенов (токенизатор модели).
- Оглавление тем вместо полных саммари в промпте — понадобится при росте числа
  тем (сотни); тогда: в промпт — список тем с датами, полный текст — скилом.
- Иерархия/дедупликация тегов тем (синонимы, нормализация сверх LLM-выдачи).
- Компакция внутри ветки активного прогона (длинные tool-дампы, многоитерационные
  прогоны) — отдельная задача; при её реализации обязательно правило безопасных
  границ для tool-пар (см. «Срез только на безопасных границах»).

## Тесты и внедрение (набросок для итерации реализации)

- Граница по `seq`: горячий хвост = `seq > max(seq_to)`; компакция сдвигает
  границу ровно на покрытый диапазон; повторная — идемпотентна по диапазону.
- Безопасные границы среза: salvaged-пара (прерванный ответ + заметка о
  неполноте) не разделяется ни при каком раскладе лимита.
- Пересборка контекста после «перезапуска» менеджера (нарратив из БД + саммари).
- Фоновый guard: один прогон на диалог; дотриггер после завершения; фейл — лог,
  диалог жив.
- `history_search`: подстрока, фильтр темы/дат, лимит, изоляция диалогов.
- Интеграционный: длинный диалог → ветка содержит блок тем + свежий хвост и не
  содержит сжатые сообщения дословно.
