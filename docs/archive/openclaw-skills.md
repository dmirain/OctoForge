# Скилы openclaw в OctoForge — анализ и дизайн импортёра

> **Статус: отложено, к реализации не планируется.** Идея сохранена на будущее;
> зависит от хранилища инструкций (см. [instructions.md](instructions.md), этап B
> в [plan.md](plan.md)). Источник фактов: локальный клон `/Users/dmirain/dev/openclaw`.

## Формат скилов openclaw

Скил = каталог с `SKILL.md` (~50 шт. в `skills/`, ещё ~20 в `extensions/`):

- **YAML-frontmatter**: `name`, `description` (текст для матчинга — именно он попадает
  в их системный промпт каталогом скилов), опционально `homepage`,
  `metadata.openclaw` (emoji, `requires.bins` — нужные бинарники, `install` — рецепты
  установки). Metadata записана flow-style YAML, парсится `yaml.safe_load`.
- **Markdown-тело**: процедурный сценарий для LLM — когда применять, какие вызовы и
  команды делать, примеры, заметки. Это текст-промпт, а не исполняемый код.

Примеры: `weather` (JSON API wttr.in через `web_fetch`/`curl`), `github` (CLI `gh`),
`summarize` (CLI-бинарь), `skill-creator` (чистая методология).

## Классификация корпуса

Тело сценария ссылается на окружение openclaw (`web_fetch`, shell-вызовы, их
внутренности). По этому признаку:

1. **HTTP-скилы** (weather, xurl, blogwatcher, gifgrep…) — вызовы веб-API. Маппятся
   на наш `external_call`/`http_request` почти как есть.
2. **CLI-скилы** (github→`gh`, summarize, spotify-player, tmux…) — нужны локальные
   бинарники и их `exec`. У нас shell-exec тула нет и не планируется (безопасность).
3. **Методологические** (skill-creator, coding-agent, security-triage…) — знание/процедура,
   работают без специального окружения.
4. **Скилы окружения openclaw** (session-logs, model-usage, clawhub…) — привязаны к их
   внутренностям, для нас бесполезны.

## Подход на будущее: офлайн-импортёр в хранилище инструкций

Их скил — это ровно наш «скил» из [instructions.md](instructions.md): текстовый
сценарий, который следует LLM. Корпус классов 1 и 3 импортируем в таблицу
`instructions` (тип `skill`), а не исполняем в их рантайме.

Отвергнутые альтернативы:

- **Рантайм-совместимость** (реализовать у себя их тулы `exec`/`web_fetch`/`browser`,
  чтобы скилы работали «как есть») — тащит shell-exec и чужое окружение, противоречит
  нашей модели (типизированные инструкции в БД, `external_call`, SSRF-гвард).
- **Ручное переписывание** нужных скилов — теряется главная ценность: объём корпуса.

### Маппинг

- `name` → `title`; `description` + тело → `content` (тело почти verbatim: LLM сам
  переведёт «use web_fetch(url)» на наш `external_call` — системный промпт уже учит
  этому). Вход эмбеддинга: title + description + content.
- `homepage` — ссылкой на источник в начале `content` (атрибуция); остальной
  `metadata.openclaw` не храним (только сигнал классификации).
- Теги: `source:openclaw` всегда; `kind:http` / `kind:methodology` — по классификации.

### Классификация при импорте (эвристика + отчёт для ручной курации)

- есть `requires.bins` или тело преимущественно про shell-бинарники → **skip**;
- ссылается на внутренности openclaw (gateway, session-logs, clawhub…) → **skip**;
- в каталоге скила есть доп. файлы-скрипты → **skip** (зависимость от файловой системы);
- иначе → **import**.
- Импортёр печатает отчёт «импортировано / пропущено с причиной» — проходим глазами,
  при желании дорабатываем эвристику или добавляем скилы вручную.

### Форма поставки (когда дойдёт)

- Парсер/классификатор — чистый тестируемый модуль
  `octoforge_core/instructions/openclaw_import.py` (frontmatter через `yaml.safe_load`;
  новая зависимость core `pyyaml`).
- Тонкий CLI: `python -m octoforge_core.instructions.openclaw_import <skills-dir>` —
  пишет через `InstructionStore` (DI), database-url из аргумента/env.
- Запуск — по требованию против локального клона, **не** сид при старте (рантайм не
  должен зависеть от чужого чекаута). Опционально: кураторский JSON-снапшот выбранных
  скилов в репо (`seeds/`), подкладывается сидом в свежие БД — «из коробки» 15–25
  боевых скилов.
- Повторный импорт идемпотентен: update по `title`, а не дубли.

### Тесты (на момент реализации)

Парсинг frontmatter (включая metadata flow-YAML), классификация по фикстурам
(http / cli / methodology / env / с файлами), идемпотентность, содержимое отчёта.
