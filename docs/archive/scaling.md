# Масштабирование: диалоги и задачи при нескольких инстансах

> Согласовано: вариант C (гибрид). Требования: минимум компонентов, быстрый ответ,
> две инсталляции одним кодом. **Статус: рекомендация, реализация поэтапно.**

## Базовый факт

Живой прогон (стрим LLM, отмена, SSE-подписчики) физически находится в памяти ровно
одного инстанса — расшарить его нельзя.

## Две инсталляции, один код

- **Standalone**: 1 инстанс + SQLite (независимые малые установки).
- **Distributed**: LB + N инстансов + Postgres.

Отличия — только конфиг (`OF_DEPLOYMENT_MODE`) и composition root:

| Аспект | Standalone | Distributed |
|---|---|---|
| БД | SQLite | Postgres |
| Владение диалогом | тривиально, lease no-op | lease + fencing CAS |
| Маршрутизация | не нужна | LB, консистентный хэш |
| Heartbeat/drain | no-op | heartbeat + graceful drain |
| Outbox, write-behind, реплей SSE | одинаково | одинаково |

## Ключевая идея (distributed): консистентный хэш на LB

LB маршрутизирует по консистентному хэшу ключа диалога (`(user_id, channel)` или user_id).
Все запросы диалога попадают на один инстанс → актор, SSE и фоновые процессы
**всегда коллокированы**: pub/sub не нужен, уведомления in-process, глобальный воркер
задач не нужен (фон исполняет pump актора-владельца), реестр владельцев не нужен.

**Компоненты: LB + инстансы + БД. Всё.**

## Скорость ответа

1. Маршрутизация O(1), без lookup'ов в БД.
2. Стрим из памяти сразу; персист — write-behind. Синхронно: user-сообщение, fencing-CAS.
3. Уведомления in-process → мгновенно; оффлайн → outbox, доставка при контакте.
4. Переподключение SSE: `?since=seq` — реплей одним запросом.

## Целевая модель (distributed)

- **LB**: консистентный хэш по ключу диалога; смена кольца → переезд минимума диалогов.
- **Инстанс**: in-memory акторы (пересборка из БД); heartbeat; graceful drain.
- **БД (Postgres)**: dialogs (+`lease_owner`, `lease_version`, `lease_expires`), messages, tasks, outbox.
- **Fencing**: CAS по `lease_version` при старте прогона; проигравший в окне кольца отклоняет, LB ретраит.
- **Падение инстанса**: lease истекает → захват, пересборка из БД; прогоны → `interrupted`
  → перезапуск с последнего user-сообщения (at-least-once, идемпотентные уведомления).
- **Отмена**: флаг `cancel_requested` в БД + проверка на итерациях.

## Грабли

1. Сплит-брейн → fencing (distributed).
2. Деплой → drain + реплей по seq.
3. Юзер оффлайн → outbox.
4. Takeover = at-least-once → идемпотентность.
5. Хэш-ключ диалога — в каждом запросе.
6. WS vs SSE ортогонален распределённости.

## Поэтапно

- **Этап 0**: standalone, один инстанс, in-memory (текущее).
- **Этап 1 (БД/auth)**: standalone + SQLite: БД — источник истины; акторы из БД; outbox; write-behind.
- **Этап 2**: distributed-профиль: Postgres; LB-хэш; lease+fencing; drain; реплей; cancel-флаг.
