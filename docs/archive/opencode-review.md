# Сравнительное исследование: opencode vs OctoForge

> Глубокий разбор [opencode](https://opencode.ai) (open-source AI coding agent,
> TypeScript-монорепо, ~380k строк) относительно OctoForge — по каждому нашему модулю.
> Зрелость, популярность и размер команды в расчёт не берутся: только механики и архитектура.
> Исследование по коду (8 параллельных разведок + спот-проверка ключевых утверждений).
> Пересечения с `docs/hermes-review.md` помечены как (↔ hermes).

## Обзор: разные профили, разные философии

**opencode** — single-user coding-агент: CLI/TUI, живёт на машине разработчика, его сила —
инструменты редактирования кода, снапшоты git-деревьев, permission-система. Архитектурный
стиль — **Effect-ts**: сервисы как `Context.Service` + `Layer`, типизированные ошибки
`Schema.TaggedErrorClass`, структурная конкурентность на файберах. Ядро сессии —
**event-sourced**: таблица `event` + проекции (`session_message` и др.), durable-инбокс
`session_pending`, реплей событий с курсора. Хостед-часть (`packages/console`) — коммерческий
LLM-gateway: workspace-тенанты, биллинг Stripe, квоты, rate-limit на Redis.

**OctoForge** — hosted multi-user диалоговый агент: Protocol-порты, DI из composition root,
asyncio-актор на диалог, fg/bg-процессы, LLM-роутер, крон, память, инструкции с эмбеддингами.

Ключевое отличие профилей: у opencode **нет ни крона, ни памяти, ни датасетов, ни
мессенджер-поверхностей** (Slack — 145-строчное демо) — это наши зоны безусловного выигрыша.
У нас нет coding-инструментов, снапшотов/отката, permission-модели, MCP, event-sourcing'а —
и далеко не всё из этого нам нужно. Ниже — по модулям.

## agent/ — луп, исполнение, события

**У них.** `session/runner/llm.ts`: внешний цикл по pending-работе, внутренний по шагам.
Шаг = выбор контекста → промоут pending-входов → авто-компакция если нужно → запрос →
стрим. LLM-события переводятся в **durable события сессии** и публикуются сериализованно
(семафор); tool-вызовы — **конкурентные файберы** в FiberSet. Ретрай: типизированная
классификация (retryable = rate-limit/provider-internal/transport), экспоненциальный backoff
с полом по `Retry-After`, ≤4 попыток, событие `RetryScheduled` (`runner/retry.ts`).
Max-steps: на последнем шаге тулзы убираются из запроса, `toolChoice:"none"` + синтетическое
сообщение → принудительный финальный ответ вместо ошибки. Отмена — `Fiber.interrupt` со
структурной уборкой; частичный текст **теряется**. Входящие сообщения во время прогона —
детерминированный двухполосный **durable inbox** (`session_pending`: steer = вставить между
шагами, queue = ждать конца busy-периода), admission идемпотентен по client-message-id.
События: ~40 схем, split durable/ephemeral, реплей с курсора `{after, follow}`,
event-sourcing с проектором в read-модель. `run-coordinator` — keyed-сериализатор
busy-периодов с doorbell против гонки check-then-idle.

**У нас.** `AgentLoop.stream()` — async-генератор типизированных событий; актор
`ConversationRunner` (нарратив + fg/bg-процессы); LLM-роутер (INJECT/START_NEW/CANCEL/
PROMOTE); salvaged-частичный ответ с `INTERRUPTED_NOTE`; события — в памяти, без персиста.

**Мы лучше:** разговорная семантика «несколько вопросов в полёте» (процессы + роутер) — у них
одна линейная история, смена темы = прерывание или новая сессия; salvaged-частичный ответ
(у них прерванный assistant фейлится и текст теряется); свёртка фоновых результатов в диалог
(у них background — только синтетический nudge); читаемость — ~850 строк чистого asyncio
против runner+publisher+projector+pending+Effect-машинерии при тех же гарантиях.

**Мы хуже:** нет ретраев в лупе — первая ошибка провайдера = Failed (↔ hermes);
max_iterations — жёсткая ошибка вместо принудительного финала; тулзы исполняются
последовательно; события не персистятся и не реплеятся (SSE-клиент при дисконнекте теряет
дельты); нет идемпотентного submit (ретрай HTTP/Telegram задвоит сообщение); нет tool-progress
событий; нет реакции на context-overflow провайдера.

**Взять:**
1. **Финал при max-iterations**: дополнительный вызов с `tools=[]` + «подведи итог» вместо
   Failed. ~Полдня, высокая ценность.
2. **Ретрай-политика в лупе** (↔ hermes `ResilientLLMClient`): классификация retryable,
   backoff с `Retry-After`, событие `RetryScheduled` для UI.
3. **Идемпотентный submit**: client message id в API/акторе, дедуп перед персистом. Полдня,
   средне-высокая ценность (Telegram-ретраи).
4. **Конкурентные тулзы**: `asyncio.gather` по tool_calls итерации, история в порядке вызовов.
   ~День, средняя ценность.
5. Событие `ToolCallProgress` (колбэк в `SkillContext` для длинных скилов).
6. Replay событий для SSE-переподключения (см. поверхности) — отложить, пока дисконнекты не
   болят.
**Не брать:** полный event-sourcing с проектором (тяжело для одноузлового SQLite-хоста),
steer/queue-полосы (наш роутер богаче), doorbell-координатор (наш инбокс актора уже даёт ту же
сериализацию).

## context/ — компакция

**У них.** `session/compaction.ts`: триггеры — проактивный (**реальный usage** последнего
assistant-сообщения ≥ `context_limit − buffer`), реактивный (provider context-overflow до
первого вывода → компакция → рестарт шага, однократно), ручной `/compact` (durable
pending-вход). Механика: сериализация истории в плоский текст, хвост ~8000 токенов дословно
(срез отодвигается к границе user-сообщения), **rolling anchored summary** — один
обновляемый саммари по структурному шаблону (Objective / Details / Work State / Next Move /
Relevant Files, «сохраняй точные пути/команды/ошибки»), результат — сообщение типа
`compaction`; загрузка истории — от последнего checkpoint'а. Компакция **синхронная**,
блокирует шаг.

**У нас.** Трёхуровневая модель (архив → саммари с темами → горячий хвост `seq > max(seq_to)`),
**фоновая** asyncio-компакция вне горячего пути, безопасные границы, salvaged-пары,
`history_search` по архиву, лимит в символах.

**Мы лучше:** компакция не блокирует диалог (фейл = warning-лог, у них фейл авто-компакции
фейлит шаг пользователя); хвост — настоящие сообщения с ролями, у них «recent» — плоская
сериализация с усечением tool-выводов до 2000 символов (потеря точности внутри сохранённого
куска); архив доступен агенту через `history_search` (у них пре-checkpoint строки для модели
мертвы); несколько саммари с тегами тем — лучше для долгоживущих мультиюзерных диалогов, чем
один блоб; порт `ContextCompactor` + Noop для тестов.

**Мы хуже:** нет учёта токенов вообще (↔ hermes — у них триггер от реального usage против
лимита модели с headroom); символьный триггер только по хвосту — игнорирует системный промпт,
схемы скилов и растущий блок тем; нет реактивной компакции при overflow-ошибке; блок тем
растёт без bounds (rolling merge решает это константным размером); нет ручной компакции;
их шаблон саммари структурнее нашего free-form.

**Взять:**
1. Usage в порте LLM + **токенный триггер** с headroom (`OF_MODEL_CONTEXT_TOKENS −
   OF_CONTEXT_BUFFER_TOKENS`), символы — фолбэк. (↔ hermes, фундамент.)
2. **Реактивная компакция**: context-overflow → синхронная компакция → один ретрай прогона.
   Метод `compact_now` на порте, вызов из runner'а. (↔ hermes.)
3. **Rolling merge**: передавать предыдущее саммари в суммаризацию с инструкцией обновления —
   закрывает риск «сотни тем» из `docs/context.md`. (↔ hermes итеративное обновление.)
4. Их структурный шаблон (Objective/State/Next move + правило «точные идентификаторы») —
   дополнить наш `TOPICS:`. Промпт-only, тривиально.
5. Ручная компакция (скил `history_compact` или команда) поверх `compact_now`.
**Не брать:** синхронную компакцию в шаге, сериализованный `recent`-checkpoint (наш дословный
хвост строго лучше), event-sourced checkpoint-сообщения.

## llm/ — провайдер-слой

**У них.** Собственные протоколы (`packages/ai/src/protocols/`, 15 штук: anthropic-messages,
openai-chat/responses, gemini, bedrock…) — `Protocol` владеет телом запроса и стейт-машиной
стрима; `Route` = Protocol + Endpoint + Auth + Transport; Vercel AI SDK — только мост для
экзотики. Классификатор ошибок `provider-error.ts`: статус + коды + ~25 regex'ов →
RateLimit/Quota/Auth/ContentPolicy/InvalidRequest(с подклассом **context-overflow**)/
ProviderInternal/Transport; редактирование секретов в контекстах ошибок; парсинг
rate-limit заголовков и `retry-after`. Cache-policy: «auto» — cache hints на последний тул,
последний system-блок, последнее user-сообщение (только для anthropic-messages/bedrock,
4 брейкпоинта, TTL 5m/1h). models.dev — каталог моделей (цены, лимиты) с кэшем. Title
генерируется aux-вызовом; `generateObject` — принудительный синтетический тул (та же техника,
что в нашем роутере).

**У нас.** Порт `LLMClient` (2 метода) + 200-строчный OpenAI-compatible клиент; порты
`EmbeddingClient`/`RerankerClient` с локальными бэкендами. Без классификации ошибок, ретраев,
usage, кэша.

**Мы лучше:** эмбеддинги/реранкер как первоклассные порты с локальными бэкендами (у них нет
ничего); простота (200 строк против ~8k + Effect-машинерия); фейк порта в тестах тривиален.

**Мы хуже:** `raise_for_status()` выпускает сырые httpx-ошибки — нельзя отличить 429 от 401
от overflow; следствие — нет ни ретраев, ни overflow-компакции; нет usage; нет stall-таймаута
между SSE-чтениями; нет aux-модели для роутера/компактора; нет редактирования секретов в
ошибках (ключи могут утекать в логи через текст исключений).

**Взять (всё ↔ hermes, подтверждено вторым источником):**
1. **Таксономия ошибок `llm/errors.py`** — портировать суть `provider-error.ts`
   (rate_limit(retry_after)/auth/quota/context_overflow/provider_internal/transport),
   классификация в `openai.py` из статуса и тела. ~150 строк, ключ к ретраям и overflow.
2. Декоратор `RetryingLLMClient` — backoff, пол по `Retry-After`, только retryable-классы.
3. Overflow → компакция → рестарт (см. context).
4. Usage capture (`stream_options.include_usage`) → `StreamFinished` → персист.
5. Per-read stall-таймаут в `stream()`. ~20 строк.
6. Aux-модель (`OF_AUX_LLM_*`) в роутер и компактор — чистый DI.
7. Редактирование секретов в контекстах ошибок — вместе с п.1.
**Отложить:** models.dev-каталог (достаточно `context_window` в конфиге), cache-breakpoints
(когда появится Anthropic — копировать их раскладку: последний тул + последний system +
последнее user-сообщение, cap 4).

## skills/ + instructions/ + datasets/ + net/ — инструменты и безопасность

**У них.** Тулзы через `Tool.make` со схемой (Effect Schema): **одна схема = и валидация
аргументов, и JSON-schema для провайдера**; валидируется даже output. Реестр со скоупами и
неймспейсами. Дефолтный режим — **CodeMode**: большинство тулзов схлопываются в один
мета-тул `execute`, модель пишет JS, вызывающий остальные (экономия схем в контексте).
`ToolOutputStore`: большие выводы — в стор, модели — ограниченный превью. Хуки before/after
с мутабельными событиями. **Permission-система**: упорядоченные правила
`{action, resource, effect: allow|ask|deny}` с wildcard'ами, last-match-wins, дефолт `ask`;
источники — конфиг агента + персистные правила проекта; `ask` блокирует тул до ответа
(once/always/reject-с-фидбэком модели). MCP: полноценный клиент (stdio + streamable-HTTP,
OAuth DCR+PKCE, толерантность к битым outputSchema, реконсиляция реестра на `ToolsChanged`).
Скилы — файловые `SKILL.md` с frontmatter, progressive disclosure (в промпте только
id+description, тело — по требованию). webfetch **без SSRF-гварда** — безопасность целиком на
человеке, отвечающем на permission-промпты.

**У нас.** Скилы за `Skill` Protocol, JSON-schema — только для промпта (валидация аргументов
размазана по скилам); `SsrfGuard` (resolve-every-IP, блок неглобальных, без редиректов);
whitelist-авторизация из composition root, секреты не видны LLM; инструкции в БД с
эмбеддинг-поиском и реранком; датасеты с JSON-схемой и owner-изоляцией. Без permission-модели,
хуков, MCP, shell/file-туlzов.

**Мы лучше:** сетевой SSRF-гвард на уровне резолвинга (у них его нет вообще — их модель
«спросить человека» непереносима на hosted multi-user); изоляция кредешелов (whitelist +
подстановка `{user_id}`); мультитенантность, прошитая через `SkillContext.user_id` в SQL;
агентно-сохраняемые инструкции в БД с семантическим поиском (у них — файловый markdown,
непригодный для хостеда).

**Мы хуже:** нет permission-правил (даже статических allow/deny); нет центральной валидации
аргументов против схемы; нет хуков (а аудит вызовов скилов хостед-агенту нужен больше, чем
CLI); нет MCP (вся экосистема тул-серверов закрыта); плоские строковые выводы со слепым
усечением 4000 символов — нет ни схемы вывода, ни spill/retrieve больших результатов.

**Взять:**
1. **Порт `SkillHooks`** (before/after, мутабельные input/result, вызов в лупе) — первый
   consumer: аудит-лог (user_id, dialog_id, skill, размер результата). ~100 строк, высокая
   ценность для хостеда.
2. **Центральная валидация аргументов** против `spec.parameters_schema` (jsonschema) в лупе —
   единообразные ошибки, схема становится источником истины.
3. **Порт `PermissionPolicy`**: `check(user_id, action, resources) -> allow|deny` (без `ask`
   в v1 — фоновым процессам некого спрашивать); статические правила из конфига + персистные
   per-user. Средняя стоимость, нужно с ростом пользователей.
4. **MCP за портом, только streamable-HTTP** (stdio небезопасен на хостед-боксе): per-user
   токены, тулзы как DYNAMIC-скилы с неймспейсом `mcp_{server}_`, реконсиляция на изменениях.
   Высокая стоимость, высокая стратегическая ценность.
5. **Spill больших выводов**: полный результат в стор, модели — превью + ссылка для
   `history_search`. Средняя ценность.
6. Progressive disclosure инструкций (↔ hermes: индекс в промпт + загрузка тела).
**Не брать сейчас:** CodeMode (песочница JS на тенанта — огромная секьюрити-поверхность),
stdio-MCP, файловые скилы.

## db/ — персист

**У них.** SQLite через drizzle, синхронные драйверы (bun:sqlite / node:sqlite) за семафором;
прагмы при старте: **WAL, synchronous=NORMAL, busy_timeout=5000, foreign_keys=ON**; схема
co-located с доменами, миграции — TS-файлы, baseline генерируется; event-sourcing (`event` +
проекции, проекции disposable — есть миграции-«ресеты», просто `DELETE FROM` проекций);
durable inbox `session_pending`; `event_sequence` upsert для seq; epoch-millis время.
Рестарт: `time_suspended` + CAS `consumeSuspended` → at-most-once resume.

**У нас.** SQLAlchemy **async** + Alembic, `UTCDateTime` форсит UTC на уровне типа, атомарный
`seq` подзапросом, порты на сторы модулей. Без прагм, без FTS, без recovery, без retention.

**Мы лучше:** async-драйвер сквозняком (у них блокирующий sync за семафором — для CLI норм,
для хостеда нет); UTC-корректность на уровне типа (у них голые epoch-millis); Alembic
autogenerate против рукописных DDL; эмбеддинги и векторный поиск (у них ноль); наши порты
легче их Service/Layer-графа при той же выразительности.

**Мы хуже:** нет SQLite-прагм — и `datasets/store.py` тихо полагается на FK-каскады, которые
SQLite по умолчанию **не исполняет** (их блок прагм — готовый шаблон); нет durable inbox /
restart recovery (у них suspend→consume→resume CAS-цепочка); нет soft-archive диалогов;
состояние `tasks` не восстанавливается.

**Взять:**
1. **Прагмы event-listener'ом в `db/engine.py`** (WAL, busy_timeout, synchronous=NORMAL,
   foreign_keys=ON). ~15 строк + тест, высокая ценность (чинит FK-опасность и contention).
   (↔ hermes.)
2. **Suspend/resume для задач**: `suspend_active()`/`list_suspended()`/`consume_suspended()`
   на порте `TaskStore` (CAS по колонке `suspended_at`), suspend из `runner.stop()`, resume
   из warmup'а `ConversationManager`. Закрывает осиротение PENDING/RUNNING без полного
   event-sourcing'а. (↔ hermes startup-recovery, но эта форма чище.)
3. Soft-archive диалогов (`archived_at`) + фильтр листинга. Одна миграция, гигиена.
4. FTS5 external-content над `messages` (↔ hermes) — когда LIKE станет измеримо больно.
**Не брать:** epoch-millis (наш UTCDateTime лучше), event-sourcing целиком (дurable-inbox
даёт ту же надёжность без проектора), рукописные миграции.

## tasks/ — фон и субагенты

**У них.** Субагент = дочерняя **сессия** с `parentID`: полная изоляция контекста, своя
модель, свой агент-конфиг; ограничение по идентичности агента + permission-check; **лимит
глубины** обходом цепочки parentID (дефолт 1); результат — последний assistant-текст;
foreground: `job.block` возвращает как tool-output, при прерывании — конверсия в background
с инъекцией финала в родителя синтетическим сообщением. `job.ts` — process-local реестр с
токеном settle (устаревший файбер не перезапишет), **явно недолговечный**: «рестарт теряет
всё, нужен отдельный durable slice». Snapshot/revert: git-tree снапшоты на шаг, выборочное
восстановление путей, revert сам отменяем; file-mutation — per-path мьютекс + CAS
compare-then-write.

**У нас.** Фоновые процессы в акторе: durable `Task`-строки, `result_delivered` exactly-once,
outcome-цепочка `TaskOutcomeListener`, CANCELLED + salvage, лимит `OF_MAX_PROCESSES`.
Глубина спавна не учитывается (bg-процесс получает `task_spawner` — вложенность возможна и
ограничена только общим лимитом). Размер результата не ограничен. Восстановления при
рестарте нет.

**Мы лучше:** долговечность — наши Task-строки реальное состояние в БД с exactly-once
доставкой; их Job явно in-memory и теряет всё (они восстанавливают только сессии, не job'ы);
outcome-фан-аут через порт (у них обработка завершения захардкожена в subagent-тул); salvage
частичного ответа; честный отказ при лимите с перечнем активных задач.

**Мы хуже:** нет restart recovery (↔ выше, у них есть рабочий CAS-паттерн); нет учёта глубины
спавна (↔ hermes); нет бюджета размера результата; нет конверсии fg→bg при прерывании
(наша отмена терминальна).

**Взять:**
1. Suspend/resume (см. db/) — их `restart.ts` + `store.ts:67-86` как шаблон CAS.
2. **Depth-guard**: `depth` в `Task.input`, отказ при `≥ OF_MAX_SPAWN_DEPTH` (дефолт 1) —
   рядом с существующей проверкой лимита. (↔ hermes.)
3. **Бюджет результата**: усечение в `_resolve_task` с маркером «[truncated]» и конфигом
   `OF_TASK_RESULT_MAX_CHARS`. (↔ hermes.)
4. Аудит гонки doorbell: проверить тестом, что `_Submit`, пришедший во время финализации
   процесса, не теряется (requeue остатков частично покрывает).
5. Токен settle — пропустить (наши uuid-ключи делают невозможным reuse id).
**Не переносимо:** git-tree снапшоты/revert и file-CAS (нет файловых мутаций; если появится
undo для датасетов — их модель «путь→версия» это референс).

## web/ + telegram — поверхности

**У них.** Schema-first протокол: один пакет `protocol` (Effect HttpApi, ~28 групп
эндпоинтов) — источник истины для сервера, сгенерированных клиентов и OpenAPI. SSE с
heartbeat 15s, **публичный манифест событий** (фильтр шины), fan-out в **ограниченные
отбрасывающие очереди** (capacity 4096, медленный подписчик убивается `SubscriberOverflow`).
Auth — один shared password (Basic или `?auth_token=` для EventSource). TUI **не встраивает
ядро** — ходит по HTTP+SSE в отдельный процесс сервера; sdk-next — embedded-режим: роутер как
fetch-хендлер без сокетов. Slack — 145-строчное демо (новое сообщение на событие, без
стрима). Share — публичные ссылки (вестигиально в этом дереве).

**У нас.** FastAPI: messages/cancel/SSE-events + cron API; trusted `X-User-Id`; статичный
чат-UI (fetch+ReadableStream ради заголовка); telegram-адаптер с портом-клиентом,
throttle-правками, tag-safe HTML-чанкингом, прогревом для крона, standalone-режимом на общем
composition root'е.

**Мы лучше:** мультитенантность by design (у них сервер строго single-tenant с глобальной
шиной и одним паролем); наш Telegram-мост сильнее их Slack-интеграции на порядок (правки
черновика, статус-строки, чанкинг против «новое сообщение на событие»); маркеры процессов —
первоклассные в обеих поверхностях; standalone на общем composition root'е проще их
sdk-next fake-fetch трюка.

**Мы хуже:** нет никакого auth (у них хотя бы shared password + query-токен); нет
схемы-контракта событий — payload'ы SSE собираются руками в `api/sse.py`, каждая новая
поверхность переинтерпретирует события (Telegram-рендерер уже вторая копия); **нет
history-endpoint'а** — перезагрузка web-страницы визуально теряет диалог; очереди
подписчиков runner'а безграничны (один зависший таб раздувает память); нет resume по `seq`.

**Взять:**
1. **Токен-аутентификация**: `OF_API_TOKEN` (или таблица токенов, см. auth ниже), Bearer или
   `?auth_token=`; `X-User-Id` остаётся идентичностью. ~День, высокая ценность.
2. **`GET /api/dialog/history`** — гидратация UI при загрузке из персистного нарратива. ~День,
   высокая ценность.
3. **Ограниченные очереди подписчиков** с drop-and-close (`asyncio.Queue(maxsize=N)`,
   переполнение → отписка). Часы, страховка памяти.
4. **Типизированная схема событий** (pydantic discriminated union в core, зеркалит
   `LoopEvent`) — сериализация в одном месте для web + telegram + будущего SDK. 1–2 дня,
   убивает дрейф переинтерпретации.
5. Resume по `seq` (`Last-Event-ID`/`?since=`) после п.2.
**Не брать:** codegen-тулычейн, registration-файлы сервисов, share-ссылки (пока).

## Аутентификация и мультитенантность (наш X-User-Id против их console)

**У них.** Полноценный control-plane (`packages/console`): account → workspace → user
(роли, monthly limits); OAuth (GitHub/Google) с мерджем по email; device-flow OAuth для CLI;
API-ключи `sk-...` (**открытым текстом в БД**, lookup по равенству); LLM-gateway с
rate-limit'ами (Redis, per-key/per-IP), месячными $-лимитами на workspace и юзера, квотами
подписки, фейловером провайдеров, Stripe-биллингом; BYOK-креды — тоже открытым текстом.
Изоляция — тот же приём, что у нас: `workspaceID`-колонка + фильтр в каждом запросе,
но tenant идёт через ambient-контекст (AsyncLocalStorage), а не явным параметром.

**У нас.** Никакого auth: доверенный заголовок `X-User-Id`, изоляция `user_id`-колонкой в SQL,
идентичность Telegram выводится сервером из апдейта (`tg:<id>`), web-канал — строка из
localStorage. Нет ролей, квот, админки.

**Мы лучше:** явное против ambient (наш `user_id` — параметр через порты, tenant-граница
аудируема типами); честный шов — одна зависимость `deps.py`, один пункт замены; у нас ещё нет
долга «ключи открытым текстом» — начнём сразу с хэшей; их gateway-экономика (Stripe, квоты)
не нужна self-hosted агенту.

**Мы хуже:** подделка личности = один заголовок; нет per-user лимитов (noisy neighbor сжигает
общий LLM-бюджет; `OF_MAX_PROCESSES` глобален); нет админской поверхности; web-канал без
идентичности вообще.

**Взять (минимально жизнеспособный auth, не их стек):**
1. **Таблица токенов** (`token_hash`, `user_id`, `revoked_at`): выдача `of-<random>`,
   проверка SHA-256-lookup'ом в `get_user_id` (`deps.py`) — хэши, не plaintext. `X-User-Id`
   оставить за dev-флагом. ~День; остальной код не трогаем — идентичность остаётся строкой.
2. **Per-user лимит процессов** вместо глобального `OF_MAX_PROCESSES` — in-memory счётчик.
   Часы, закрывает noisy neighbor.
3. **Серверное выведение идентичности** на всех каналах (как уже в Telegram): сервер резолвит
   user_id из креда, клиентский id не доверяем.
**Не брать:** device-flow OAuth, workspaces/роли/Stripe — не наш профиль; BYOK-стор (позже,
с шифрованием, если появятся per-user ключи провайдеров).

## Фичи opencode без аналога у нас вообще

- **Event-sourcing сессий** (события как истина, disposable-проекции, реплей с курсора) —
  мощно, но тяжело; брать только идею durable inbox'а, не проектор.
- **Snapshot/revert git-деревьев** и **file-mutation CAS** — непереносимо без файловых
  мутаций; референс для будущего undo.
- **Permission-ruleset** (allow|ask|deny, last-match, персистные правила) — брать в форме
  порта без `ask`.
- **CodeMode** (модель пишет JS поверх тулзов) — экономия контекста реальна, но песочница
  на тенанта слишком дорога; идея «один мета-тул» интересна в перспективе.
- **MCP-клиент** с реконсиляцией реестра — брать (HTTP-only).
- **Schema-first протокол + codegen клиентов** — брать в форме pydantic-схемы событий, не
  кодогенерации.
- **Effect-ts** (сервисы/слои/типизированные ошибки/структурная конкурентность) — их ответ
  на тем же вопросы, что наши порты+asyncio; переносить в Python нечего, наши решения легче.
- **Control-plane** (billing/квоты/workspaces) — не наш продукт.
- **TUI** — не нужен.

## Итог: приоритизированные рекомендации

Отсортировано по ценность/стоимость; (↔ hermes) = уже в рекомендациях hermes-review,
здесь подтверждено вторым независимым источником — это сильнейшие кандидаты.

**Волна 1 — дёшево, закрывает дыры:**
1. SQLite-прагмы (WAL/busy_timeout/foreign_keys) — чинит тихую FK-опасность. (↔ hermes)
2. Финал-саммари при max-iterations вместо Failed.
3. Ограниченные очереди подписчиков runner'а (drop-and-close).
4. Идемпотентный submit по client message id.
5. Depth-guard и бюджет результата для фоновых процессов. (↔ hermes)
6. Per-user лимит процессов.
7. Stall-таймаут SSE-чтений в LLM-клиенте. (↔ hermes)

**Волна 2 — надёжность хостеда:**
8. Таксономия ошибок LLM + `RetryingLLMClient` + `RetryScheduled`. (↔ hermes)
9. Usage capture → токенный триггер компакции с headroom; реактивная компакция при overflow.
   (↔ hermes)
10. Suspend/resume задач (CAS `suspended_at`) — закрывает осиротение при рестарте. (↔ hermes
    startup-recovery; форма opencode чище ledger'а hermes.)
11. Токен-аутентификация (hashed) + серверное выведение идентичности.
12. `GET /api/dialog/history` + resume по `seq`; типизированная схема событий.
13. `SkillHooks` + центральная валидация аргументов скилов.
14. Rolling-merge саммари + структурный шаблон компакции. (↔ hermes)

**Волна 3 — стратегия:**
15. MCP за портом (streamable-HTTP only, per-user токены, DYNAMIC-скилы с неймспейсом).
16. `PermissionPolicy` (allow/deny, статика + персист per-user).
17. FTS5 + spill больших выводов скилов. (↔ hermes)
18. Aux-модель для роутера/компактора. (↔ hermes)
19. Конкурентное исполнение тулзов итерации.
20. Soft-archive диалогов.

**Сознательно не берём:** event-sourcing с проектором, git-снапшоты/revert, CodeMode,
stdio-MCP, Effect-стиль, codegen-протокол, Stripe/workspaces/billing, файловые скилы,
TUI, share-ссылки.
