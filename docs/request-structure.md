# Структура запроса к LLM основного прогона

> Собрано по коду на 2026-07-21: сборка ветки — `core/src/octoforge_core/agent/runner.py`
> (`_start_new`), отправка — `agent/loop.py` (`stream(history, tools=registry.specs())`).
> Размеры замерены скриптом на текущих текстах; токены — оценка 4 chars/токен (тот же
> прокси, что у `CompactorConfig`).
>
> Пре-поиск **удалён 2026-07-21** (см. `docs/instructions.md`, раздел «Пре-поиск скилов
> до прогона») — заметки на второй позиции больше нет. Дата переехала из системного
> промпта в конверт последнего сообщения ветки (prefix-cache, см.
> `docs/prompt-caching.md`); саммари — rolling merge (одна запись на диалог).

## Порядок сборки

Массив `messages` ветки процесса:

```
[0] system    — системный промпт (байт-стабильный, без даты)
[1] system    — блок rolling-саммари прошлых тем (опционально)
[2..] user/assistant/tool — «горячий хвост» переписки дословно,
      вперемешку со служебными system-заметками; замыкается trail-сообщением;
      ПОСЛЕДНЕЕ сообщение ветки — с конвертом текущей даты UTC
      (`[Current date and time: … (UTC)]\n<текст>`)
```

Поле `tools` запроса (не сообщение) — спеки всех тулов, отправляется на КАЖДОЙ итерации
петли: после исполнения тулов весь массив + схема уходят в LLM заново.

## Таблица частей

| Порядок | Часть | Тип(ы) сообщений | Состав | Размер | ~Токены |
|---|---|---|---|---|---|
| 0 (отдельное поле) | Тулы, 19 шт. | не сообщение — поле `tools` | JSON-спеки cron×5, memory×3, data×3, history_search, task×2, web_search, http_request, external_call, skills_search, instruction_save | 10 670 chars | ~2 670 |
| 1 | Системный промпт | `system` (всегда первый) | `DEFAULT_SYSTEM_PROMPT` (5 мета-правил), байт-стабильный | ~950 chars | ~240 |
| 2 | Блок тем | `system` (одно сообщение, опционально) | одно rolling-саммари диалога: `[seq N-M] (topics: ...) текст` | 0, константный (merge) | — |
| 3 | Горячий хвост | `user` / `assistant` / `tool` + `system`-заметки | дословная переписка `seq > max(seq_to)`: сообщения пользователя, финалы и промежуточные ответы модели (с `tool_calls`), результаты тулов (с `tool_call_id`) | ≤ 12 000 chars (`OF_CONTEXT_HOT_MAX_CHARS`) | ≤ ~3 000 |
| 3а | Служебные заметки | `system` | `INTERRUPTED_NOTE` (71 char), уведомления «фоновая задача завершена» | десятки–сотни chars | — |
| 4 | Trail / репорт-надж / инъекции | `user` | входящее сообщение процесса; `REPORT_NUDGE` в репорт-прогоне; инъекции роутера через `LoopControl` | — | — |
| 4а | Конверт даты | префикс последнего сообщения | `[Current date and time: … (UTC)]\n` — только в ветке, нарратив/персист чистые | ~40 chars | ~10 |

Самые тяжёлые тулы: `history_search` ~250 ток, `task_create` и `data_put` ~245 ток,
`data_query` ~220 ток, `memory_store` ~190 ток; мелкие (`task_list`, `cron_pause`) — ~50 ток.

## Итоги

- Постоянный «налог» каждой итерации: системный промпт + тулы ≈ 11 600 chars / ~2 900 ток
  (байт-стабильный префикс — кешируется провайдером).
- Переменная часть: хвост ≈ до ~12 000 chars / ~3 000 ток;
  переполнение хвоста уходит в саммари фоновой компакцией (цель 6 000 chars,
  `OF_CONTEXT_COMPACT_TARGET_CHARS`).
- Типичный запрос диалога: ~12–25 тыс. chars / ~3–6 тыс. токенов.

## Соседние запросы (не основной прогон)

- **Роутер** (`LLMRouter`, на каждое входящее сообщение): `system` — роутерный промпт
  (~1 365 chars / ~340 ток) + список активных процессов, `user` — входящее сообщение,
  тул `route` в поле `tools`. One-shot `complete()`.
- **Фоновый процесс** (`task_create` без `schedule`, крон-выстрел): ветка начинается с `system`
  (`BACKGROUND_TASK_PROMPT`, ~100 chars) + `user` (промпт задачи с конвертом даты),
  дальше тот же шаблон, что у основного прогона.
- **Компакция** (фоновая, не процесс): `system` — `SUMMARY_SYSTEM_PROMPT`, `user` —
  предыдущее саммари + сегмент архива (rolling merge). One-shot `complete()`.

## Роли в хвосте: assistant vs tool

- `assistant` — слова модели: промежуточное сообщение с `tool_calls` («вызови тулы»,
  прогон продолжается) или финал без `tool_calls` (ответ пользователю, прогон кончился).
- `tool` — результат исполнения скила, привязан к вызову через `tool_call_id`; за
  assistant с N `tool_calls` обязаны идти ровно N tool-сообщений (отменённый вызов
  получает заглушку `CANCELLED_OUTPUT` — парность не нарушается). Ошибки скилов тоже
  возвращаются tool-сообщением с префиксом ошибки, а не исключением.
