# Стриминг и раннее исполнение тулов (eager tool execution)

> Исследование opencode и openclaw + наш дизайн. **Статус: реализовано**
> (eager-исполнение тулов + idle-watchdog стрима).
> Источники: anomalyco/opencode (GitHub, ветка dev), локальный клон
> `/Users/dmirain/dev/openclaw` (июль 2026).

## Итоги исследования

### opencode — исполняет тулы до конца сообщения

Гипотеза «ответ обрабатывается по частям» подтверждена:

- Тул запускается, как только его аргументы полностью достриманы (событие
  `tool-call`), не дожидаясь конца сообщения: fire-and-forget в AI SDK runtime
  (`executeToolCall` без await; `finish` задерживается, пока `outstandingToolResults`
  не опустеет) и явный `FiberSet.run(startImmediately)` в нативном рантайме
  (`session/llm/native-runtime.ts:114-137`). Несколько тулов — конкурентно.
- Результаты сливаются в общий поток событий через очередь; ре-запрос к модели —
  только следующей итерацией после конца шага (инкрементальность ограничена шагом).
- Процессор **не парсит частичный JSON** аргументов: ему достаточно «вызов начался»
  (pending в UI) и «вызов готов» (полный input) — `session/processor.ts:315-413`.
- Дельты текста — транзиентные (только шина), персист — целых part'ов по завершении.
- Мид-стрим защиты: doom-loop детект, ранний обрыв при переполнении контекста.

### openclaw — ждёт полного сообщения

- Исполнение **только** при `stopReason === "toolUse"`; иначе tool-блоки вырезаются
  (`removeNonExecutableToolCalls`, `agent-loop.ts:82-88`) — защита от усечённого
  стрима.
- Инкрементальность — в событиях (`toolcall_start/delta/end` от провайдеров),
  repair-парсинге аргументов и доставке в UI, не в исполнении.
- Единственное сокращение latency — `eager_input_streaming` на стороне Anthropic API.

### Как реализовано

Текст стримим дельтами (`TextDelta`); tool_calls копятся по индексам, но слот
закрывается, как только дельты переходят на следующий `index` (последний — на
`finish`): валидные аргументы → событие `ToolCallReady`, битый JSON →
`ToolCallBroken` (в финальном сообщении вызов остаётся с пустыми аргументами).
Петля на `Ready` немедленно запускает исполнение (конкурентно, результаты — через
очередь, события по мере готовности), а в историю tool-сообщения пишет строго в
порядке вызовов. На отмене mid-stream interrupted-сообщение сохраняет пришедшие
tool_calls, и на каждый пишется tool-ответ «cancelled» или реальный результат —
осиротевших результатов нет. Поверх этого — idle-watchdog стрима (таймаут паузы
между событиями, `OF_LLM_STREAM_IDLE_TIMEOUT_SECONDS`). Провайдер без
инкрементальных дельт — fallback на старт всех вызовов после `StreamFinished`.

## Дизайн eager-исполнения (реализован)

Берём из opencode: запуск по готовности аргументов, конкурентное исполнение, слив
через очередь, ожидание всех задач в конце шага. Из openclaw: защиту от битых
аргументов и «неломаемую историю» на отмене.

1. **События LLM-стрима** (`llm/events.py`, `llm/openai.py`):
   `ToolCallStarted(index, call_id, name)` — появились id+имя у дельты индекса;
   `ToolCallReady(call)` — аргументы индекса достриманы и валидно распарсились
   (конец вызова = переход дельт на следующий index; последний закрывается на
   `finish`); `ToolCallBroken(index, call_id, name, error, raw)` — JSON не собрался.
   `StreamFinished(message)` остаётся источником истины для истории.
   Отдельно: `RetryScheduled(attempt, delay_seconds, reason)` — клиентский
   ретрай транзиентного сбоя (см. design.md «Ошибки LLM и ретраи»); петля
   транслирует его в LoopEvent без влияния на историю.
2. **Петля** (`agent/loop.py`): на `Ready` — немедленно `asyncio.create_task` +
   `ToolCallRequested`; результаты через `asyncio.Queue`, события по мере готовности;
   в конце шага — ожидание всех задач; **в историю tool-сообщения строго в порядке
   вызовов** после assistant-сообщения (детерминизм при конкурентном исполнении).
   `Broken` → tool-сообщение с ошибкой без исполнения (история не ломается).
3. **Отмена mid-stream**: новые `Ready` не стартуют; запущенные отменяются;
   interrupted-сообщение сохраняет пришедшие tool_calls + на каждый — tool-ответ
   «cancelled» или реальный результат.
4. **Fallback**: провайдер без инкрементальных дельт → `Ready` пачкой на `finish` =
   сегодняшнее поведение.

## Что решено НЕ брать — с ценностью каждого решения

1. **Partial-JSON парсинг аргументов на каждой дельте** (openclaw: `repairJson` +
   `partial-json` каскад, `packages/ai/src/utils/json-parse.ts:34-147`).
   *Что даёт*: UI видит аргументы, заполняющиеся вживую; починка «кривого» JSON от
   слабых моделей спасает вызовы, которые иначе упали бы.
   *Почему нет*: для eager-исполнения не нужно (opencode обходится «начался/готов»);
   парсер-зависимость и сложность. *Когда*: слабая локальная модель с битым JSON или
   прогресс аргументов в UI.
2. **`eager_input_streaming`** (флаг Anthropic API, `anthropic.ts:1649-1651`).
   *Что даёт*: модель отдаёт дельты аргументов раньше и крупнее — меньше latency до
   готовых аргументов. *Почему нет*: Anthropic-специфика, наш клиент
   OpenAI-совместимый. *Когда*: появится Anthropic-провайдер.
3. **Doom-loop детект** (opencode: 3 одинаковых вызова подряд → стоп/вопрос,
   `processor.ts:353-380`). *Что даёт*: мид-стрим защита от зацикливания модели —
   экономия токенов и времени. *Почему нет*: нужна политика реакции (отмена? вопрос
   пользователю?); грубый предохранитель уже есть — `max_iterations`. Открытый бэклог.
4. ~~**Throttle + single-flight доставка дельт и markdown-aware чанкер**~~ — **закрыто**
   Telegram-адаптером (`telegram/bridge.py`: throttle-правки черновика
   `OF_TELEGRAM_EDIT_THROTTLE_SECONDS`, чанкер 4096, `markdown.py`: срез без разрыва
   тегов).
5. **Mid-stream abort по silent/heartbeat-токенам** (у openclaw — сознательно
   post-hoc). *Что даёт*: ранняя остановка, когда модель уже «сказала» NO_REPLY.
   *Почему нет*: post-hoc фильтрация проще и безопаснее (дешёвая генерация vs
   рассинхрон транскрипта). Открытый бэклог (post-hoc вариант).
6. **Structured-output ранний выход** (opencode: вызов спец-тула = финальный ответ).
   *Что даёт*: детерминированный финал без «догадки» по тексту. *Почему нет*: нет
   контракта структурированного ответа. *Когда*: если введём structured output.
7. **Deferred event buffer** (openclaw: буфер событий до терминального для моделей с
   refusal-контрактом; refusal → стрим отбрасывается). *Что даёт*: «откат» уже
   показанного стрима при модерации провайдера. *Почему нет*: у наших провайдеров
   нет такого контракта; тяжёлый механизм. *Когда*: появится refusal в стриме.
8. ~~**Idle-watchdog стрима**~~ — **реализовано**: пауза между событиями стрима
   (включая ожидание первого) ограничена `stream_idle_timeout` в `AgentLoop`
   (конфиг `OF_LLM_STREAM_IDLE_TIMEOUT_SECONDS`, дефолт 120, 0 = выключен);
   таймаут закрывает стрим, отменяет запущенные тулы и завершает прогон
   `Failed("LLM stream idle timeout")`.
9. **Activity-heartbeat долгих тулов** (openclaw: пинг каждые 60с из работающего
   тула). *Что даёт*: долгий вызов не выглядит зависшим для вочдога и UI.
   *Почему нет*: вочдог (п.8) следит за стримом LLM, а не за тулами — исполнение
   тулов он не трогает; пинги нужны только для UI-индикации. Открытый бэклог.
10. **Колбэк прогресса из работающего тула** (opencode `metadata()` — тул стримит
    промежуточный статус в UI). *Что даёт*: живой прогресс долгих операций.
    *Почему нет*: требует расширения Tool API. *Когда*: появятся реально долгие
    скилы (отчёты, агрегации).

## Уже совпадает с лучшими практиками

- Durable/transient: дельты — только в SSE, персистим целые сообщения (tail-pointer).
- Ошибки тулов — данными для LLM (`error: ...`), а не исключением наружу.
