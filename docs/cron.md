# Крон-задачи (периодические задания)

> Согласованные решения. **Статус: принято к реализации позже** (после БД).
> Модель вызова — через инструкции, см. [instructions.md](instructions.md).

## Сценарий

«Готовь каждое утро отчёт» → агент вызывает тул крон-сервиса через `external_call`
(контракт нашёл в каталоге инструкций) → запись в `cron_jobs` → планировщик в срок
дёргает ядро → в диалоге стартует фоновый процесс → отчёт приходит уведомлением.

## Крон-сервис

Подсистема приложения (модуль; вынос в отдельный процесс возможен без смены механизмов):
свой HTTP API, таблица `cron_jobs`, цикл планировщика. Для ядра — внешний сервис,
описанный **тулом в сторе инструкций** (сид-запись): никаких выделенных скилов
`cron_create/list/delete` — агент вызывает API через `external_call`.

- **cron_jobs**: `id`, `user_id`, `channel`, `title`, `schedule` (cron), `timezone` (IANA,
  default UTC), `prompt`, `enabled`, `next_fire_at`, `last_fire_at`, `claimed_by`, `created_at`.
  Все `*_at` — UTC; таймзона — для вычисления расписания («утро» — локальное утро юзера).
- **API**: `POST /jobs`, `GET /jobs`, `DELETE /jobs/{id}`, `POST /jobs/{id}/pause|resume`
  (user-scoped; для агента — как у тулов, служебная авторизация из белого списка).

## Выстрел

Планировщик дёргает ядро по HTTP: `POST {core}/dialogs/{key}/wake` (служебный токен) →
фоновый процесс в диалоге (см. [process-model.md](process-model.md)) с `prompt` задачи →
завершение → уведомление пользователю. Distributed: вызов через LB, хэш-ключ →
инстанс-владелец (см. [scaling.md](scaling.md)). Standalone: in-process ярлык.
Выстрел подчиняется лимиту процессов; переполнение → отложенное уведомление о невозможности запуска.

## Надёжность

- Exactly-once: CAS-захват due-задач (`claimed_by` + lease TTL).
- Пропущенные выстрелы: coalesce до одного с пометкой о пропусках.
- `next_fire_at` пересчитывается после каждого выстрела.
