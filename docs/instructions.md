# Инструкции: знания, скилы, тулы и датасеты в едином хранилище

> Согласованная модель. **Статус: частично реализовано (этап B)**.
> Отменяет типизацию скилов BASIC/DYNAMIC из ранних документов.
>
> Реализовано: обособленный пакет `core/instructions/` за фасадом
> `InstructionService` (хранение/поиск/ранжирование knowledge|skill|tool,
> локальная реализация SQL + cosine + буст точного title, сидирование);
> core-исполнитель `net/external.py` (рендер шаблонов, whitelist-авторизация,
> SSRF-гвард `net/guard.py`); рантайм-тулы `instructions_search`,
> `instruction_save`, `external_call`; порт `EmbeddingClient` +
> OpenAI-совместимый клиент.
> Осталось: влияние `usage_count`/`success_count` на ранг (полная формула
> 70/30 + MMR), http-реализация фасада (выделенный сервис), датасеты (этап C).

## Типы сущностей

1. **Знание (`knowledge`)** — факт, актуальный для всех («API X требует заголовок Y»).
   **Не память**: память по диалогам проектируется отдельно. Глобально.
2. **Скил (`skill`)** — сценарий действий: какие внешние вызовы и в какой последовательности
   использовать. Строгий текстовый формат шагов; следует LLM. Глобально.
3. **Тул (`tool`)** — описание внешнего вызова: имя, метод, url-шаблон, схема параметров,
   тип авторизации (внутренняя подставляется исполнителем по белому списку base-url). Глобально.
4. **Датасет (`dataset`)** — дескриптор структурированного хранилища пользователя: назначение,
   `schema` записи, как писать/читать/агрегировать, `retention`. **Per-user всегда.**
   См. [data-store.md](data-store.md).

Первые три типа — **глобальные** (общая база: научился у одного — пригодится другому).
Датасет — per-user: это данные пользователя, а не общая инструкция.

Таблица `instructions` (knowledge/skill/tool): `id`, `type`, `title`, `content`, `embedding`,
`tags`, `version`, `usage_count`, `success_count`, `created_at`, `updated_at`.
Датасеты и их записи — отдельные таблицы, см. [data-store.md](data-store.md).

## Рантайм-тулы (код, всегда в контексте)

1. `instructions_search(query)` — вектор + ранжирование → top-k сущностей всех типов.
2. `instruction_save(type, title, content, tags?)` — создать/обновить сущность.
3. `external_call(name, params)` — исполнить вызов по имени тула из стора.
4. `user_message` — общение с пользователем.
5. `data_put(dataset, record)` / `data_query(dataset, filter, limit?)` — работа с датасетами
   (валидация по схеме и owner-изоляция — исполнителем).

## Цикл агента

Запрос → поиск → релевантные знания/скилы/тулы/датасеты в контексте → агент выбирает:
ответить из знаний / следовать скилу (external_call по шагам) / вызвать тул /
записать или прочитать датасет / сохранить новую сущность.

## Поиск и эмбеддинги

- Embeddings endpoint (OpenAI-совместимый), конфиг рядом с LLM.
- Standalone: cosine brute-force по таблице (или sqlite-vec). Distributed: pgvector + tsvector
  (гибридный поиск), rerank; `usage_count`/`success_count` влияют на ранг.

## Сидирование

Базовые тулы (generic http, cron API) + скилы-примеры — сид-данными, не кодом.

## Модульность: выделение в сервис, замена реализации

Всё, что связано с хранением и поиском инструкций, — самодостаточный пакет
`core/instructions/` за единым фасадом `InstructionService` (Protocol):
`search` / `save` / `get_by_name`. Модуль только хранит, ищет и ранжирует;
**исполнение — на стороне core**: внешние вызовы выполняет core-исполнитель,
читающий tool-записи через фасад.

- Петля и скилы зависят только от фасада; SQL, эмбеддинги и ранжирование — детали
  реализации внутри пакета.
- DTO фасада — JSON-совместимые объекты: границу можно поднять в HTTP без смены
  вызовов (выделенный сервис инструкций, реализация фасада HTTP-клиентом).
- Реализация подменяется в composition root: локальная (SQL + cosine) сейчас;
  pgvector/внешний поиск — позже, без изменений остального кода.
- Таблицы модуля — его собственность: вынос в сервис не тянет чужие таблицы.
- Конфиг модуля (top-k, embedding endpoint) приходит конструктором из composition
  root, не читается из env напрямую; белый список base-url — конфиг исполнителя
  в composition root, к модулю отношения не имеет.

## Безопасность

- `external_call` подставляет внутреннюю авторизацию только для белого списка base-url
  (composition root); произвольные тул-записи её не получают.
- Формат сценария строгий (шаги с именованными вызовами и шаблонами параметров);
  для критичных скилов позже возможен исполняемый формат.
- Доступ к датасетам — только владельцу (проверяет исполнитель, не LLM).

## Риски и меры (из обсуждения)

- Нерелевантная выдача → гибридный поиск, rerank, статистика успехов по сущностям.
- Недетерминизм следования сценарию → строгий формат шагов; для критичных — исполняемый формат позже.
- Эмбеддинги — новая внешняя зависимость (endpoint, стоимость, задержка на запрос).
