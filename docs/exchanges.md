# Обмены: новая модель ядра диалога

**Статус:** проектирование → реализация (28.07.2026). Заменяет разметку веток конвертами,
описанную в «Процессная модель» `design.md`. Пока фазы не выкачены, актуальным остаётся
описание в `design.md`; по мере выката переносим сюда.

## Зачем

Диалог сегодня — один плоский хронологический нарратив, который одновременно служит журналом
событий, промптом каждого процесса и (неявно) ответом на вопрос «кто кому должен ответить».
Третья роль в данных не выражена: связка «вопрос → кто его закрывает» живёт только в памяти
актора (`_covered_ids`, `_injected_ids`, `start_watermark`, `_wrap_epoch`, поля процесса) и
переводится в промпт строковыми конвертами в момент сборки ветки.

Отсюда серия однотипных инцидентов и заплаток к ним:

| Симптом | Чем подпёрли |
|---|---|
| вопрос втянут mid-run и проигнорирован | `MID_RUN_NOTE_TEMPLATE` |
| два процесса ответили на оба вопроса | `HANDLED_ELSEWHERE_NOTE_TEMPLATE` |
| очередник не понял, что отвечает он | `ANSWER_THIS_NOTE_TEMPLATE` |
| конверты устаревают без роста нарратива | `_wrap_epoch` |
| сообщение потерялось | requeue по водяной метке |
| два ответа на один и тот же вопрос | (не подпёрли — инцидент 28.07) |

Шесть механизмов вокруг одного отсутствующего понятия. При этом связка **уже есть в БД**
(`tasks.source_message_id`, `messages.task_id`), но при сборке ветки выбрасывается — и модель
получает ленту, где вопрос и ответ стоят в произвольном порядке.

## Понятие: обмен

**Обмен (exchange)** — обязательство перед пользователем: его вопрос, все уточнения к нему
(с обеих сторон) и итоговый ответ. Диалог — последовательность обменов; лента сообщений — лишь
способ их показать.

Ключевое разделение: **статус задачи ≠ статус обмена**. Задача (`tasks`) описывает прогон:
он может завершиться (DONE), не закрыв обмен, — например, агент задал уточняющий вопрос.
Обмен описывает обязательство и живёт дольше любого прогона.

### Состояния

```
OPEN ──────────► IN_PROGRESS ──────────► ANSWERED
 ▲                   │      ▲              (закрыт ответом)
 │                   │      │
 │           ask_user │      │ пришла реплика пользователя
 │                   ▼      │
 └─── прогон упал ── AWAITING_USER
                      │
                      ├── отменён пользователем ──► CANCELLED
                      └── прогон провалился ──────► FAILED
```

- `OPEN` — вопрос есть, никто не работает. **Единственное состояние, означающее работу для
  системы**: предикат «что надо доделать» = обмены в OPEN без владельца. Он же обслуживает
  восстановление после рестарта (сегодня связка теряется полностью).
- `IN_PROGRESS` — обменом владеет живой процесс (`owner_task_id`).
- `AWAITING_USER` — агент задал уточняющий вопрос. **Работа для пользователя, не для системы**:
  в предикат «доделать» не входит, но обмен не закрыт и виден и агенту, и оператору.
- `ANSWERED` / `CANCELLED` / `FAILED` — терминальные.

### Хранение

Состояние `AWAITING_USER` порождается действием, а не текстом, поэтому вычислить обмен из
сообщений нельзя — он **строка в БД**: таблица `exchanges` + `messages.exchange_id`.
Историческим сообщениям обмен не назначается (NULL) — они рендерятся как обычная лента.

## Маршрутизация: как сообщение находит свой обмен

Слои от бесплатного и точного к умному:

1. **Детерминированные сигналы (без LLM).** Пользователь ответил *реплаем* на сообщение бота →
   обмен известен точно (`reply_to_message_id` → сообщение → обмен). Нет ни одного открытого
   обмена → новый обмен, роутер не вызывается.
2. **Правильный фрейм для LLM.** Роутер решает не про процессы (деталь реализации), а про
   обмены — сущность с человеческим текстом:
   ```
   Открытые обмены:
     #2 «Какая погода?» — ждёт от пользователя ответа на «В каком городе?» (40 сек назад)
     #3 «Собери отчёт за неделю» — в работе (2 мин)
   Сообщение: «Москва»
   ```
3. **Ограниченный выбор.** Кандидаты — открытые обмены за разумное окно; закрытые в выбор не
   попадают.
4. **Безопасный дефолт — новый обмен.** Ошибка «лишний обмен» = лишний ответ (шум, виден и
   поправим). Ошибка «прицепили не туда» = чужой прогон съел вопрос, ответа нет (тишина).
   Принцип прежний: дубль лучше молчания.
5. **Измеримость.** Решение роутера логируется вместе со входом (какие обмены предлагались) —
   сегодня на вопрос «почему бот так решил» ответа нет в принципе.

Операции роутера схлопываются до трёх: `NEW` (новый обмен), `CONTINUE(exchange)` (сообщение
принадлежит существующему обмену — бывший INJECT и «ответ на уточнение» разом), `CANCEL(exchange)`.
Guardrail «inject убивает start_new» исчезает: сообщение принадлежит ровно одному обмену.

**Одно сообщение = один обмен.** Резать составной вопрос на два обмена не будем: классификация
ненадёжна («сделай X и потом Y» — один обмен), цена — двойной прогон, а выигрыш достигается
существующим агентским механизмом: тяжёлую часть агент сам выносит в `task_create` и отвечает
на лёгкую сразу. Решает тот, кто понял смысл, а не роутер по эвристике.

**Последовательности обменов нет.** Обмены независимы и идут параллельно: строгая очередь
была нужна только из-за одного черновика на чат (см. ниже), а с `AWAITING_USER` она давала бы
клин — обмен, ждущий пользователя, блокировал бы все следующие.

## Рендеринг ветки

Один рендерер вместо трёх конвертов. Порядок сообщений остаётся хронологическим (не врём про
время), но каждое несёт свою роль относительно **этого** прогона, выведенную из состояния
обмена:

```
user:      Почему чаек много на море?            ← закрытый обмен, обычная история
assistant: <ответ>
user:      [ТВОЯ ЗАДАЧА] Какая погода?
assistant: В каком городе?
user:      [уточнение к твоей задаче] Москва
```

Правило одно: **вопрос своего обмена помечен как задача, вопросы чужих открытых обменов — как
занятые другим прогоном, остальное — обычная история.** Входы правила — durable-состояние, а не
гонки в памяти, поэтому исчезают `_covered_ids`, `_injected_ids`, `_wrap_epoch`, `synced_epoch`
и три конверта. Водяные метки остаются как оптимизация «что нового», а не как механизм
корректности.

## Уточняющий вопрос агента

- **Явное действие:** тул `ask_user(вопрос)`. Вызов доставляет вопрос пользователю и переводит
  обмен в `AWAITING_USER`; прогон завершается, слот освобождается. Состояние живёт в обмене,
  процесс — расходник: процесс, ждущий ответа, держал бы слот неограниченно и умирал бы при
  рестарте вместе с контекстом.
- **Возобновление:** реплика пользователя маршрутизируется в тот же обмен (слои 1–2) и
  поднимает **новый** процесс; его ветка собирается из истории обмена.
- **Починка:** если модель задала вопрос обычным текстом вместо тула, следующая реплика всё
  равно уйдёт в тот обмен через роутер — состояние временно неточно, но не потеряно.
  Расхождение логируем.
- **Напоминание:** если пользователь пишет новый вопрос, а обмен в `AWAITING_USER` старше
  5 минут — отдельным сообщением уходит напоминание с цитатой своего же вопроса. Событийно,
  в момент маршрутизации; отдельного таймера не нужно. Если пользователь исчез — не напоминаем.

## Параллельные черновики

У каждого события есть владелец-обмен, поэтому транспорт держит **черновик на обмен**, а не один
на чат: в Telegram это N редактируемых сообщений (каждое реплаем на свой вопрос), в web — N живых
пузырей. Метаданные едут в конверте `ConversationEvent` (payload событий не меняется).

Следствия — то, ради чего всё и затевалось:

- **Понятие «форграунд» растворяется**: оно существовало ровно потому, что черновик один.
- **Гейт доставки `_flush_if_free` исчезает**: outbox остаётся только гарантией «нет подписчика —
  не теряем результат».
- Уточняющий вопрос из фонового обмена приходит сразу, а не ждёт конца чужого стрима.

RUN-задачи (`task_create`, крон) обменами не являются — у них нет вопроса пользователя; они
работают молча и доставляют результат через outbox, как сегодня.

## Фазы

| Фаза | Что | Критерий приёмки |
|---|---|---|
| 1 | Обмены как данные: миграция, состояния, роутер решает про обмены (слои 1–4), предикат «незакрытого» вместо requeue-эвристик | сценарий «два вопроса подряд» даёт два разных ответа |
| 2 | Один рендерер ветки; удаление трёх конвертов, множеств id, эпохи | код **похудел** — иначе это опять заплатки |
| 3 | `ask_user`, `AWAITING_USER` end-to-end, приоритет вопросов в доставке, напоминание | вопрос из фонового обмена доходит, ответ его продолжает |
| 4 | Черновик на обмен; растворение форграунда и гейта доставки | два ответа стримятся одновременно, каждый в своём сообщении |

Каждая фаза самостоятельна, деплоится отдельно и не делает хуже.
