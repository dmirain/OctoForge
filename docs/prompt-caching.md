# Кеширование промпта в LLM

## Что это такое

Это **KV-cache на стороне провайдера**: при обработке запроса модель вычисляет
attention-ключи/значения для токенов. Если начало следующего запроса (префикс)
токен-в-токен совпадает с предыдущим, провайдер переиспользует уже вычисленный
KV-cache вместо повторной обработки. Выгода двойная:

- **скорость** — заметно ниже TTFT (time to first token) на длинных промптах;
- **цена** — закешированные токены считаются со скидкой: у OpenAI примерно −50%
  на чтение, у Anthropic −90% (но запись в кеш стоит +25%), у DeepSeek — тоже
  ощутимая скидка.

Ключевое свойство: кеш работает **строго по префиксу**. Совпадение считается от
первого токена до первого расхождения — всё, что после точки изменения, из кеша
уже не берётся. Это не семантический кеш: «почти такой же» промпт не
засчитывается, нужно токенное совпадение.

Детали по провайдерам:

- **OpenAI** — автоматически, без конфигурации; кешируются префиксы от ~1024
  токенов, TTL порядка 5–10 минут простоя (до часа в горячем состоянии). Есть
  опциональный `prompt_cache_key` — помогает роутить запросы одной сессии на
  один сервер.
- **Anthropic** — явные брейкпоинты `cache_control` (до 4 штук), TTL 5 минут или
  1 час (дороже), минимальный кешируемый блок ~1024 токена.
- **Gemini** — явное API context caching; **DeepSeek** — автоматически.

## Что делать для максимальной эффективности

1. **Стабильный префикс, изменчивое — в конец.** Порядок: системный промпт →
   определения тулы/скилов → статичный контекст (память, инструкции) → история
   диалога → новое сообщение. Всё, что меняется часто, должно лежать как можно
   ближе к хвосту.
2. **Не менять список и порядок тулов между вызовами.** Дефиниции функций —
   часть префикса. Динамическое добавление/перестановка скилов на каждый ход
   убивает кеш целиком.
3. **Append-only история.** Никогда не редактировать и не переупорядочивать
   старые сообщения — только дописывать в конец. Инъекция сообщения «в середину»
   истории инвалидирует кеш от этой точки до конца.
4. **Убрать volatile-данные из системного промпта.** Текущее время с точностью
   до минуты, случайные ID, счётчики в system prompt = инвалидация кеша на
   каждый запрос. Дата раз в сутки — терпимо; timestamp — нет. Если нужно
   время — передавать его в user-сообщении.
5. **Стабилизировать результаты retrieval.** Если память/инструкции/RAG
   подставляются в контекст, их порядок и набор должны быть детерминированными
   (dedupe, стабильная сортировка, фиксированный top-k), иначе каждый ход —
   новый префикс.
6. **Консистентная сериализация.** Одинаковый порядок ключей в JSON, одинаковые
   отступы — любое «косметическое» отличие в строке промпта это промах кеша.
7. **Длинный статический префикс имеет смысл.** Выше порога ~1024 токенов
   экономия становится существенной; короткие системные промпты выгоды почти не
   дают.
8. **Держать сессию «тёплой».** TTL кеша короткий (минуты), поэтому диалоги с
   частыми ходами выигрывают больше; у Anthropic для редких обращений есть
   часовой кеш.
9. **Осторожно с компакцией/рерайтом истории.** Любая суммаризация заменяет
   кусок истории → кеш после неё инвалидируется. Это неизбежная разовая цена,
   но делать компакцию на каждый ход нельзя.

## Применительно к OctoForge

Архитектура в основном кеш-дружественная: нарратив актора append-only, история
перепроигрывается с начала каждый ход — это идеальный сценарий префикс-кеша.
Потенциальные точки потерь:

- `_with_current_date` в системном промпте процессов — меняет префикс раз в
  сутки, это нормально; главное не добавлять туда время.
- `FilePromptProvider` перечитывает файл на каждый get — само по себе безвредно,
  но если кто-то трогает файл, кеш для всех диалогов сбрасывается разом.
- Ретрайв памяти/инструкций и будущая автоинъекция памяти в контекст — тот самый
  пункт 5: без стабилизации порядка это будет главный убийца кеша.
- Компакция (`LlmContextCompactor`) — разовая инвалидация, приемлемо, но после
  неё один «дорогой» ход неизбежен.
- One-shot вызовы роутера с отдельным коротким промптом кешируются плохо — но
  они и так дешёвые.

Если когда-нибудь появятся Anthropic-модели, правила 1–3 те же, плюс
расстановка `cache_control` в конце системного блока и в конце дефиниций тулов.
Для OpenAI-совместимого бэкенда достаточно стабильного префикса — всё остальное
автоматика.
