# Процессная модель диалога и LLM-роутер

> Согласованные решения по архитектуре. **Статус: реализовано (этап E).**
> Текущая реализация — также в `design.md` («Актор диалога», «Фоновые задачи»).

## Модель процессов

**Процесс** — обработка одного вопроса: свой прогон петли со своей веткой истории. Два положения:

- **Форграунд** (ровно один активный на диалог): рассуждения и промежуточные ответы стримятся пользователю.
- **Фон (тень)**: процесс продолжается молча, без стрима; пользователь ждёт, когда система вернётся сама с результатом.

Нарратив диалога (у актора): user-сообщения + финальные ответы завершённых процессов — контекст для новых процессов.

> Диалог, внутри которого живут процессы и нарратив, — это пара (user_id, channel), см. [dialogs.md](dialogs.md).

## Правила переключения

1. Новый независимый вопрос во время прогона → текущий процесс **откладывается в фон** (НЕ отменяется), новый вопрос становится форграундом.
2. Отмена — **только по явной просьбе** пользователя.
3. Форграунд завершился → **никакого автовозврата**. Агент лишь **сообщает** об ответах/вопросах по предыдущим задачам (уведомление при завершении фонового). Вернуть задачу — только явной просьбой (`PROMOTE`).
4. Комментарий по текущему делу → инъекция в форграунд (steer).
5. **Лимит процессов** (`OF_MAX_PROCESSES`, default 5): если новый процесс не помещается в лимит даже после отмен из решения роутера — агент **предлагает отменить** что-то из активных, новый процесс не стартует.

## Роутер

Каждое входящее сообщение проходит через **роутер** (Protocol `MessageRouter`, первая реализация — `LLMRouter`). Понимает, **к каким процессам** относится сообщение, возвращает **пакет операций**. Активных процессов нет → вхолостую: `PASSTHROUGH` без LLM-вызова.

### Решения

- `RouteOp`: `action: RouteAction`, `target_id: str | None`; `RouteDecision`: `ops: tuple[RouteOp, ...]`.
- `RouteAction`: `INJECT` (комментарий в форграунд), `START_NEW` (новый форграунд; занят → текущий в фон), `CANCEL(target)`, `PROMOTE(target)` (фон → форграунд; занят → текущий в фон).

Примеры: комментарий → `[INJECT]`; новый вопрос mid-run → `[START_NEW]`; «останови всё и начни новое» → `[CANCEL(p1), CANCEL(p2), CANCEL(fg), START_NEW]`; «верни задачу X» → `[PROMOTE(x)]`. Пустой пакет = `PASSTHROUGH`.

Фолбэк при ошибке/таймауте LLM: форграунд активен → `[START_NEW]`, иначе `[]`.

### LLMRouter

- Вход: snapshot (форграунд + фоновые: id, title, status, place) + сообщение + лимит.
- Пустой snapshot → пустое решение без вызова.
- Иначе one-shot `complete()` с роутер-промптом (процессы, лимит, правила) и tool call `route(ops)`; валидация target'ов; таймаут; фолбэк.

## Актор (менеджер процессов)

- Нарратив + процессы (`dict[id, Process]`), один форграунд; broadcast — только события форграунда (+ маркеры).
- `submit`: решение роутера → применить пакет по порядку.
- **Guardrail лимита** (детерминированный): перед `START_NEW`/`PROMOTE` — если `активных − отменённых + 1 > max` → отказ + прогон-репорт «предложи отменить одну из: список».
- Завершение фонового: system-уведомление + прогон-репорт (свободен) или инъекция (занят).

## Задачи == фоновые процессы

- `Task` — запись в `TaskStore` только на время полёта: финализация остановленного
  процесса и доставка результата удаляют её; история остаётся в нарративе.
- `TaskKind`: только `RUN`; `TaskStatus` (`CANCELLED` — терминал процессов и
  `cron_jobs.last_status`, в таблицу `tasks` не пишется); `TaskStore`:
  add/get/list/mark_done/mark_failed/delete/fail_orphaned/list_undelivered.
- Спавн: `ToolContext` += порт `TaskSpawner`; остановка — порт `TaskDeleter`
  (bound-реализации в акторе).

## События

`ProcessSuspended`, `ProcessResumed`, `ProcessCompleted` — сериализация в SSE, маркеры в UI.

Источники фоновых процессов: вытеснение форграунда (`SWITCH`), спавн через `TaskSpawner`, крон-планировщик (см. [cron.md](cron.md)).

## Вне скоупа

Фон с needs_input; комментарии внутрь фоновых; кеш решений роутера; детерминированные реализации `MessageRouter`; персист в БД.

## Реализационные решения (этап E)

- **Персистится только нарратив**: user-сообщения, финальные ответы завершённых процессов,
  system-уведомления (о завершении задач, об отказе по лимиту) и salvaged-фрагменты
  прерванных ответов (с пометкой-константой о неполноте). Промежуточные
  assistant/tool-сообщения живут только в ветке процесса и в `messages` не пишутся.
- **Процессы — в памяти**: после рестарта процессы не восстанавливаются; нарратив
  пересобирается из `messages`. Побочный эффект: задачи в статусах PENDING/RUNNING
  после рестарта осиротевают (их процессы умерли) — редоставка/реанимация в бэклоге.
- **Репорт-прогоны**: system-заметка (уведомление о задаче, отказ по лимиту) при
  свободном форграунде стартует обычный fg-процесс с title="report" поверх нарратива;
  при занятом — инъектируется в форграунд. Доставка результата задачи = публикация
  заметки, затем удаление записи задачи (порядок защищает от потери результата при
  сбое персиста; краш между ними лечится редоставкой на старте).
- **Bound `TaskSpawner` / `TaskDeleter`**: порты привязаны к диалогу актором; задача
  (kind=RUN) сразу становится bg-процессом с id = task.id и собственным коротким
  системным промптом; спавн всегда в фон, при достижении лимита — текст-отказ тулу.
  Удаление активной задачи останавливает её процесс (запись убирает финализация);
  самоудаление из собственного прогона тул отклоняет через `ToolContext.owner_task_id`.
- **`ToolContext.task_spawner`/`task_deleter` опциональны** (`None` по умолчанию):
  контексты вне актора (юнит-тесты тулов, разовые выполнения) не обязаны тащить
  их; `task_create` без спавнера падает `ToolArgumentsError` с понятным текстом.
- **Глобальный `TaskRunner` и `TaskStore.next_pending` удалены**: поллер больше не
  нужен — исполнение задач = pump-процессы актора; `notify_task_done` на менеджере
  упразднён, уведомление делает сам актор по факту терминации процесса.
- **`MessageRepository.append` атомарен**: `seq` вычисляется подзапросом внутри
  INSERT — конкурирующие писатели (актор и pump'ы процессов) не ловят
  unique-конфликт по (dialog_id, seq).
- **Отмена через API** (`cancel()`) снимает только форграунд; `stop()` — все процессы.
- **Guardrail лимита детерминированный** и действует одинаково для START_NEW и
  PROMOTE: `активных − отменённых пакетом + 1 > max` → операция не выполняется,
  вместо неё — заметка-отказ (инъекция или репорт-прогон).
- **Недочитанные инъекции** процесса (drain mailbox'а в конце прогона) возвращаются
  в inbox как уже записанные в нарратив `_Submit` — повторно не персистятся,
  маршрутизируются роутером заново.
