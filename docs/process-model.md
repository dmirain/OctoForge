# Процессная модель диалога и LLM-роутер

> Согласованные решения по архитектуре. **Статус: реализовано (этап E).**
> Текущая реализация — также в `design.md` («Актор диалога», «Фоновые задачи»).

## Модель процессов

**Процесс** — обработка одного вопроса: свой прогон петли со своей веткой истории. Каждый
процесс подкреплён записью задачи (`process.id == task.id`): kind `ANSWER` — ответ на
сообщение пользователя, kind `RUN` — отложенная работа (`task_create`) и крон-выстрелы.
Два положения:

- **Форграунд** (ровно один активный на диалог): рассуждения и промежуточные ответы стримятся пользователю.
- **Фон (тень)**: процесс продолжается молча, без стрима; результат приходит отдельным
  сообщением, когда форграунд свободен.

Нарратив диалога (у актора): user-сообщения + финальные ответы завершённых процессов +
служебные заметки — контекст для новых процессов. Ветка narrative-процесса =
`[system] + снапшот нарратива (компактор) + приватный рабочий суффикс`; на границе каждой
итерации ветка перечитывает нарратив (pull-модель) — новые сообщения видны процессу
без канала инъекций.

> Диалог, внутри которого живут процессы и нарратив, — это пара (user_id, channel), см. [dialogs.md](dialogs.md).

## Правила переключения

1. Новый независимый вопрос во время прогона → текущий процесс **откладывается в фон** (НЕ отменяется), новый вопрос становится форграундом.
2. Отмена — **только по явной просьбе** пользователя.
3. Форграунд завершился → **никакого автовозврата**. Завершившийся фоновый процесс **доставляет результат** отдельным сообщением, когда форграунд свободен (outbox брокера, без LLM). Вернуть задачу — только явной просьбой: «верни задачу X» маршрутизируется как `START_NEW` (новый процесс видит весь нарратив).
4. Комментарий по текущему делу → `INJECT`: сообщение остаётся в нарративе, форграунд подхватывает его на следующей итерации (pull).
5. **Лимит процессов** (`OF_MAX_PROCESSES`, default 5): если новый процесс не помещается в лимит даже после отмен из решения роутера — процесс не стартует, а брокер доставляет **шаблонное уведомление** со списком активных (без LLM).

## Роутер

Каждое входящее сообщение проходит через **роутер** (Protocol `MessageRouter`, первая реализация — `LLMRouter`). Понимает, **к каким процессам** относится сообщение, возвращает **пакет операций**. Активных процессов нет → вхолостую: `PASSTHROUGH` без LLM-вызова.

### Решения

- `RouteOp`: `action: RouteAction`, `target_id: str | None`; `RouteDecision`: `ops: tuple[RouteOp, ...]`.
- `RouteAction`: `INJECT` (комментарий в форграунд), `START_NEW` (новый форграунд; занят → текущий в фон), `CANCEL(target)`.

Примеры: комментарий → `[INJECT]`; новый вопрос mid-run → `[START_NEW]`; «останови всё и начни новое» → `[CANCEL(p1), CANCEL(p2), CANCEL(fg), START_NEW]`; «верни задачу X» → `[START_NEW]` (свежий процесс видит весь нарратив и подхватывает тему). Пустой пакет = `PASSTHROUGH`.

Фолбэк при ошибке/таймауте LLM: форграунд активен → `[INJECT]` (сообщение подхватится на следующей итерации), иначе `[]` (= START_NEW).

### LLMRouter

- Вход: snapshot (форграунд + фоновые: id, title, status, place) + сообщение + лимит.
- Пустой snapshot → пустое решение без вызова.
- Иначе one-shot `complete()` с роутер-промптом (процессы, лимит, правила) и tool call `route(ops)`; валидация target'ов; таймаут; фолбэк.

## Актор (брокер сообщений)

- Нарратив + процессы (`dict[id, Process]`), один форграунд, outbox доставки; broadcast — события форграунда (+ маркеры) и доставки из outbox.
- `submit`: решение роутера → применить пакет по порядку.
- **Guardrail лимита** (детерминированный): перед `START_NEW` — если `активных − отменённых + 1 > max` → отказ + шаблонное уведомление брокера со списком активных.
- Завершение фонового: результат встаёт в outbox и доставляется целиком (DONE → текст + `Finished`, FAILED → `Failed`), когда форграунд свободен; финал форграунда уже отстримлен — только проставляется `delivered_at`.

## Задачи == процессы

- `Task` — запись в `TaskStore`, хранится вечно (DONE/FAILED/CANCELLED тоже);
  доставку результата фиксирует `delivered_at`; финал связывается с задачей
  через `messages.task_id`.
- Родительская связь задачи — в `input`: крон-выстрел несёт `{cron_job_id,
  fired_at}`, answer-задача — `{source_message_id}` (id user-сообщения-вопроса;
  `ChatMessage.id` — id строки в БД, чистые DB-метаданные, из равенства
  исключён: построенное в коде сообщение равно загруженному).
- `TaskKind`: `RUN` (task_create, крон) и `ANSWER` (ответ на сообщение пользователя —
  внутренняя механика, в `task_list` не видна); `TaskStatus` включает `CANCELLED`
  (терминал процессов и `cron_jobs.last_status`); `TaskStore`:
  add/get/list/mark_done/mark_failed/mark_cancelled/delete/list_orphaned/
  list_undelivered/mark_delivered.
- Спавн: `ToolContext` += порт `TaskSpawner`; остановка — порт `TaskDeleter`
  (bound-реализации в акторе).

## События

`ProcessSuspended`, `ProcessCompleted` — сериализация в SSE, маркеры в UI.

Источники фоновых процессов: вытеснение форграунда (`START_NEW` при занятом fg), спавн через `TaskSpawner`, крон-планировщик (см. [cron.md](cron.md)), перезапуск осиротевших задач при startup-recovery.

## Вне скоупа

Фон с needs_input; адресные комментарии внутрь конкретного фонового процесса; кеш решений роутера; детерминированные реализации `MessageRouter`.

## Реализационные решения (этап E)

- **Персистится только нарратив**: user-сообщения, финальные ответы завершённых процессов
  (с `task_id` сформировавшей задачи), шаблонные уведомления брокера (отказ по лимиту)
  и salvaged-фрагменты прерванных ответов (с пометкой-константой о неполноте). Промежуточные
  assistant/tool-сообщения живут только в ветке процесса и в `messages` не пишутся.
- **Процессы — в памяти**: после рестарта нарратив пересобирается из `messages`, а
  осиротевшие задачи (PENDING/RUNNING — их процессы умерли) перезапускаются recovery
  фоновыми процессами (`restart_task`), недоставленные результаты редоставляются
  (см. «Фоновые задачи» в [design.md](design.md)).
- **Pull-модель вместо канала инъекций**: ветка narrative-процесса =
  `[system] + снапшот нарратива от компактора + приватный рабочий суффикс`
  (assistant/tool-сообщения прогона, переживают каждый re-sync). На каждом
  `IterationStarted` narrative-часть перечитывается: новые сообщения (пользовательские,
  финалы других задач, заметки брокера) видны автоматически; без изменений ветка
  байт-идентична (prefix-cache), конверт даты пересчитывается только при изменении
  нарратива. `LoopControl` сведён к флагу отмены.
- **Доставка без LLM**: завершение фоновой задачи складывается в outbox
  (`_pending_deliveries`) и уходит подписчикам целиком (DONE → `TextDelta` полного
  результата + `Finished`, FAILED → `Failed`), когда форграунд свободен и подписан
  хотя бы один транспорт; после отправки проставляется `delivered_at`. Одна задача =
  одно сообщение. Финал
  форграунда пользователь уже видел стримом — только проставляется `delivered_at`.
  Отказы по лимиту — константные шаблоны брокера (assistant-сообщение в нарративе +
  та же доставка через outbox).
- **Без подписчиков outbox ждёт**: broadcast в ноль очередей никому не доходит, поэтому
  `delivered_at` не ставится и результат сливается при следующем `subscribe()`
  (подписка кладёт в инбокс `_Flush`). Иначе результат, завершившийся при отключённом
  транспорте, терялся бы навсегда — startup-sweep пропускает проштампованную строку.
- **Bound `TaskSpawner` / `TaskDeleter`**: порты привязаны к диалогу актором; задача
  (kind=RUN) сразу становится bg-процессом с id = task.id и собственным коротким
  системным промптом; спавн всегда в фон, при достижении лимита — текст-отказ тулу.
  Остановка активной задачи гасит её процесс (финализация помечает запись CANCELLED,
  строка остаётся в базе); самоудаление из собственного прогона тул отклоняет через
  `ToolContext.owner_task_id`.
- **`ToolContext.task_spawner`/`task_deleter` опциональны** (`None` по умолчанию):
  контексты вне актора (юнит-тесты тулов, разовые выполнения) не обязаны тащить
  их; `task_create` без спавнера падает `ToolArgumentsError` с понятным текстом.
- **Глобальный `TaskRunner` и `TaskStore.next_pending` удалены**: поллер больше не
  нужен — исполнение задач = pump-процессы актора; `notify_task_done` на менеджере
  упразднён, уведомление делает сам актор по факту терминации процесса.
- **`MessageRepository.append` атомарен**: `seq` вычисляется подзапросом внутри
  INSERT — конкурирующие писатели (актор и pump'ы процессов) не ловят
  unique-конфликт по (dialog_id, seq).
- **Отмена через API** (`cancel()`) снимает только форграунд; `stop()` — все процессы.
- **Guardrail лимита детерминированный** и действует только на START_NEW:
  `активных − отменённых пакетом + 1 > max` → процесс не создаётся, вместо него —
  шаблонное уведомление брокера со списком активных (доставляется через outbox как
  обычное сообщение).
- **Водяная метка**: процесс помнит длину нарратива на момент последнего sync'а;
  при финализации user-сообщения за меткой, не покрытые собственной answer-задачей
  и не бывшие чистыми командами (CANCEL без INJECT), возвращаются в inbox
  как уже записанные в нарратив `_Submit` — повторно не персистятся,
  маршрутизируются роутером заново (сообщение не теряется, даже если процесс
  завершился, не увидев его).
