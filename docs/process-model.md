# Процессная модель диалога и LLM-роутер

> Согласованные решения по архитектуре. **Статус: принято к реализации позже.**
> Документ описывает целевую модель; текущая реализация — в `design.md`.

## Модель процессов

**Процесс** — обработка одного вопроса: свой прогон петли со своей веткой истории. Два положения:

- **Форграунд** (ровно один активный на диалог): рассуждения и промежуточные ответы стримятся пользователю.
- **Фон (тень)**: процесс продолжается молча, без стрима; пользователь ждёт, когда система вернётся сама с результатом.

Нарратив диалога (у актора): user-сообщения + финальные ответы завершённых процессов — контекст для новых процессов.

> Диалог, внутри которого живут процессы и нарратив, — это пара (user_id, channel), см. [dialogs.md](dialogs.md).

## Правила переключения

1. Новый независимый вопрос во время прогона → текущий процесс **откладывается в фон** (НЕ отменяется), новый вопрос становится форграундом.
2. Отмена — **только по явной просьбе** пользователя.
3. Форграунд завершился → **никакого автовозврата**. Агент лишь **сообщает** об ответах/вопросах по предыдущим задачам (уведомление при завершении фонового). Вернуть задачу — только явной просьбой (`PROMOTE`).
4. Комментарий по текущему делу → инъекция в форграунд (steer).
5. **Лимит процессов** (`OF_MAX_PROCESSES`, default 5): если новый процесс не помещается в лимит даже после отмен из решения роутера — агент **предлагает отменить** что-то из активных, новый процесс не стартует.

## Роутер

Каждое входящее сообщение проходит через **роутер** (Protocol `MessageRouter`, первая реализация — `LLMRouter`). Понимает, **к каким процессам** относится сообщение, возвращает **пакет операций**. Активных процессов нет → вхолостую: `PASSTHROUGH` без LLM-вызова.

### Решения

- `RouteOp`: `action: RouteAction`, `target_id: str | None`; `RouteDecision`: `ops: tuple[RouteOp, ...]`.
- `RouteAction`: `INJECT` (комментарий в форграунд), `START_NEW` (новый форграунд; занят → текущий в фон), `CANCEL(target)`, `PROMOTE(target)` (фон → форграунд; занят → текущий в фон).

Примеры: комментарий → `[INJECT]`; новый вопрос mid-run → `[START_NEW]`; «останови всё и начни новое» → `[CANCEL(p1), CANCEL(p2), CANCEL(fg), START_NEW]`; «верни задачу X» → `[PROMOTE(x)]`. Пустой пакет = `PASSTHROUGH`.

Фолбэк при ошибке/таймауте LLM: форграунд активен → `[START_NEW]`, иначе `[]`.

### LLMRouter

- Вход: snapshot (форграунд + фоновые: id, title, status, place) + сообщение + лимит.
- Пустой snapshot → пустое решение без вызова.
- Иначе one-shot `complete()` с роутер-промптом (процессы, лимит, правила) и tool call `route(ops)`; валидация target'ов; таймаут; фолбэк.

## Актор (менеджер процессов)

- Нарратив + процессы (`dict[id, Process]`), один форграунд; broadcast — только события форграунда (+ маркеры).
- `submit`: решение роутера → применить пакет по порядку.
- **Guardrail лимита** (детерминированный): перед `START_NEW`/`PROMOTE` — если `активных − отменённых + 1 > max` → отказ + прогон-репорт «предложи отменить одну из: список».
- Завершение фонового: system-уведомление + прогон-репорт (свободен) или инъекция (занят).

## Задачи == фоновые процессы

- `Task` — запись в `TaskStore`; исполнение — pump-процесс актора; глобальный `TaskRunner` упраздняется.
- `TaskKind`: только `RUN`; `TaskStatus` += `CANCELLED`; `TaskStore` += `cancel/is_cancelled/count_active`.
- Спавн: `SkillContext` += порт `TaskSpawner` (реализует `ConversationManager`, проверка лимита → текст-отказ).

## События

`ProcessSuspended`, `ProcessResumed`, `ProcessCompleted` — сериализация в SSE, маркеры в UI.

Источники фоновых процессов: вытеснение форграунда (`SWITCH`), спавн через `TaskSpawner`, крон-планировщик (см. [cron.md](cron.md)).

## Вне скоупа

Фон с needs_input; комментарии внутрь фоновых; кеш решений роутера; детерминированные реализации `MessageRouter`; персист в БД.
